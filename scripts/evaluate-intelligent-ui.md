# Intelligent UI evaluation runner

This runner uses synthetic tasks and explicit local adapters. `prepare` sends no model requests. `run` invokes the selected adapter, which may use a real provider and incur its normal cost. Do not use an untrusted adapter. Never include credentials in result files.

```powershell
node scripts/evaluate-intelligent-ui.mjs prepare --models provider/model-a,provider/model-b --output .verification/intelligent-ui-baseline --split development
node scripts/evaluate-intelligent-ui.mjs run --output .verification/intelligent-ui-baseline --adapter C:/absolute/path/to/adapter.mjs --max-runs 4
node scripts/evaluate-intelligent-ui.mjs summarize --output .verification/intelligent-ui-baseline
```

Prepare fixes the suite hash, baseline tool hash, model IDs, policy versions, model settings and repetition count before execution. Use `--settings settings.json` for explicit model settings; `{}` records reliance on provider/SDK defaults and does not guarantee identical provider defaults over time. Do not modify the manifest to relabel failed tasks. Prepare a separate directory for heldout evaluation (`--split heldout`). Once heldout outputs inform tuning, retire the whole exposed family from heldout and add new families under a new suite version.

`--max-runs` limits new runs and allows bounded resumption. The manifest byte hash, baseline hash, adapter file hash and adapter dependency description must match on resume. A truncated or invalid result line stops processing instead of silently discarding a failed run. `run.lock` prevents concurrent writers; after a crash, verify its process has stopped before manually removing that file. Keep the frozen source hash/commit and dependency description with the report; hashes do not lock remote provider revisions. Set the runner deadline with `--timeout-ms` during prepare; later changes require a new run directory.

Adapters must also export `async describeEvaluation({ policyVersions, modelSettings, baselinePath })`, returning a JSON object with the complete effective tool schemas/system prompts, applied settings and hashes of transitive source/SDK dependencies. This declaration is captured before the first model call and compared on resume. Do not include credentials. The adapter is trusted to enumerate its dependencies accurately; review that function and retain the repository revision. An isolated model run defaults to `scope: isolated-model-generation`; it reports `attempt.evidence.generationValid` separately while production usability metrics remain pending. Use `--scope production-end-to-end` only with an adapter that actually exercises the runtime, browser and persisted state.

The adapter exports `async runTask({ task, model, policyVersion, repetition, signal, modelSettings, baselinePath })`. Only send the `user` text from `task.turns` and the appropriate frozen tool/context to the model. `task.label`, `task.checks`, IDs, split and family are evaluation metadata, never model instructions. Each turn must execute in the same conversation; repetitions/tasks use independent sessions. Prior turns' assistant/tool results and saved UI state must be retained. Baseline uses the complete frozen `phase1-tool.json` definition. Candidate `intent-4` uses the same schema with the versioned decision guidance; prepare defaults to `phase1,intent-4`. New input-protocol experiments require a distinct protocol label, such as `plan-1` or `plan-2`; their effective prompts also include the current decision-policy version and are frozen in the dependency description.

Policy `intent-4` retains `intent-2`'s numeric controls, known constraints, static label and focused clarification guidance. It explicitly separates adjustable values from unresolved business rules: asking for a calculator does not authorize inventing a calculation policy, manual answer fields, or an unrequested menu of hypothetical rules. Explicitly requested hypothetical exploration is supported; rules already present in context are reused. Its short tool description also requires missing rates or coefficients to be clarified; editable fields do not authorize invented defaults, and user-supplied initial values must be retained. These are model instructions, not a deterministic semantic guarantee. Preserve historical `intent-1`/`intent-2`/`intent-3` reports and frozen outputs unchanged. Reproducing those runs requires their original frozen source and adapter; prepare a new directory for revised guidance rather than relabeling or resuming old runs with current source.

The forward development targets are frozen in `docs/verification/intelligent-ui-phase2-evaluation-targets-2026-10-29.json`. They were recorded after the phase1 baseline and earlier small candidate probes, before compiler 2.3 and its full comparison; do not describe the earlier work as preregistered. Historical v2.10 isolated results bypassed production admission; preserve those discrepancies and do not reinterpret them as product successes.

The current live adapter verifies the installed SDK admission patch and uses `bindAnswerOutputAdmission` plus SDK `runToolCall`. Every synthetic user turn owns one budget, shared across all model requests in that turn: at most three admitted calls, one correction, and 60 seconds from the first UI attempt. Original Plan arguments are checked before SDK coercion; compiler repairability and SDK schema errors settle through the same production hook. A denied or expired update cannot replace the prior in-memory surface. A second denied call terminates evaluation as `admission-stopped`, which remains a failed task rather than a user cancellation. Each attempt records its admission snapshot. The separate evaluation request/token/tool caps still apply and are frozen in settings.

This is still `isolated-model-generation`: permission review, source CAS, disk receipts, browser operations, cancellation through the full app and saved followups require separate runtime tests. Only explicitly synthetic failures capture bounded generated arguments (at most 64,000 characters, with truncation flagged), including pre-validation Plan errors. Raw arguments are never included in model feedback or added to production diagnostics. `decision-boundary-cases.json` supplies a separate development-only suite with missing-rule, explicit exploration, known-context and ordinary-text contrasts; it does not replace the heldout set.

After a complete development run, `node scripts/check-intelligent-ui-calculations.mjs --directory <run-directory> --output <new-report.json>` applies offline numeric trajectories taken from the original task checks. This makes no model requests and does not modify the frozen runs. It follows the same result expression across changed inputs; unrelated constants cannot satisfy a trajectory. Unique numeric defaults and explicit control types/options associate controls with the checks; ambiguous or unsupported representations remain `unmapped`, not successful. Results are post-hoc calculation evidence only, not label semantics, browser/save/followup checks or human acceptance. A checkbox representing two colors can therefore remain unmapped even when valid; review it instead of silently changing the denominator. These oracle records must never be included in model context.

For a separate frozen suite, supply both `--suite <suite.json>` and `--oracles <oracles.json>` to the calculation checker. It verifies the manifest byte hash, matching suite and complete run records; oracle IDs must cover every selected UI task exactly once. Multiple expected UI turns currently require a separate per-turn oracle format and are rejected rather than silently scoring the first. Version 3 reports retain failed/no-call records and split counts by model and policy. Preserve old reports; use a new output path. Hashes record which expectations were used but do not prove they were authored before model outputs.

The 2026-10-30 heldout comparison is frozen in `docs/verification/intelligent-ui-phase2-heldout-plan-2026-10-30.json`: 26 heldout families (10 UI, 6 text, 5 clarification, 5 unsupported), two models, phase1 versus Plan2 2.4/intent-4, three repetitions, 312 runs. `heldout-cases-2026-10-30.json` preserves the original 20 heldout tasks and adds six families from `heldout-supplement-2026-10-30.json`. Numeric expectations in `heldout-calculation-oracles-2026-10-30.json` were fixed before these model calls. The original development suite and its reports remain unchanged. Domain separation does not imply unseen arithmetic primitives or unrestricted generalization; human semantics and complete product workflows remain separate requirements.

Suite `natural-language-2` labels each multi-turn request with `turn.label`; only `turn.user` may be sent as user content. For example a one-off calculation followed by a request for adjustable inputs is `text` then `ui`. A task's overall label cannot stand in for all turns. Single-turn suites may omit the turn label and use `task.label`; older multi-turn suites without turn labels remain pending for task usability, rather than inferring intent retrospectively. Preserve old run suites/manifests and prepare a new directory for the revised suite.

Format 2 reports keep `turnSelection` and per-task turn details. Task `selectionMiss` means at least one expected UI turn lacked a call in that turn; `falseTrigger` means at least one expected text turn generated UI, including text turns inside an overall UI task. The per-turn metrics count only known labels, explicitly disclose label coverage, and leave unobserved turns pending. A task that stops before later turns still fails end-to-end usability without inventing the missing model choice. UI success requires every expected UI turn's first/final attempt to be committed as appropriate, no UI on text/clarify/unsupported turns, and agreement on `choiceCorrect` as well as semantic correctness. Aggregate technical and reviewer judgments must cover the whole conversation; multiple UI turns are not interchangeable evidence. `selectedGenerationFailure` remains a whole-task failure metric among tasks that selected UI in an expected UI turn, and therefore includes incorrect response choices elsewhere in that task. Inspect turn metrics to distinguish routing from generation failures.

Return the entire task outcome, including turns where no tool was called:

```js
{
  outcome: 'completed', // or provider-error, timeout, cancelled
  turns: [{ user: 'exact synthetic prompt', assistant: 'final answer', durationMs: 1200,
    uiAttempts: [{ toolCallId: 'sdk-id', toolName: 'piora_render_ui', committed: true, errorCode: undefined }] }],
  technical: { calculation: true, interaction: true, saved: true, reload: true, followup: true },
  reviews: [
    { reviewer: 'independent-human-1', semanticCorrect: true, choiceCorrect: true },
    { reviewer: 'independent-human-2', semanticCorrect: true, choiceCorrect: true }
  ]
}
```

`committed` must be backed by the real save/commit evidence, not merely valid JSON. Capture malformed calls and tool errors as attempts, using actual SDK call IDs; deduplicate transport replays only, not new calls. Map provider failure/timeout/cancellation to a result retaining earlier turns, partial current answer and attempts. `AbortSignal` is cooperative: the adapter must cancel its transport and return a timeout outcome rather than abandon a live request. Unexpected adapter exceptions stop the runner; investigate and resume rather than treating an incomplete run as success.

Omit unverified technical checks and human reviews. Missing evidence produces pending metrics; a model's self-score or schema validation is not acceptance. Two reviewers must actually judge independently; disagreement remains pending until documented adjudication. For clarification tasks set `clarificationUseful`; for unsupported tasks use `choiceCorrect`. When a task takes multiple attempts, `firstAttemptTechnical` and each review's `firstAttemptCorrect` are needed to assess a successful first attempt separately. Failed or absent attempts already prove first-attempt failure.

Use `outcome: 'cancelled', cancellationSource: 'user'` only for an actual explicit user cancellation. It is reported separately. Model stops, provider errors and timeouts stay in end-to-end denominators. Unsupported/either tasks are reported separately from capability-internal UI success. The report retains durations for all UI tasks, including failures; it splits no-call misses from failed generation and records independent family count separately from repetitions. Intervals are deliberately unclaimed until adequate family/category counts and a cluster method are preregistered. The initial 60-task suite is a prototype, not a production generalization guarantee.

This runner does not yet independently verify technical claims made by an adapter. Use browser/state receipts and independent expected values from `task.checks`, attach their evidence to the run/report, and review the adapter. Freeze acceptance thresholds after baseline collection and before candidate tuning; no threshold is fabricated by this command.

## Connected workflow probe

`node scripts/probe-intelligent-ui-workflow.mjs --model provider/model --task tests/fixtures/intelligent-ui/workflow-courses.json --output .verification/new-probe --protocol plan-2` uses the configured provider in a new isolated agent/workspace. Only the Intelligent UI generation tool is enabled. It runs the production SDK/wrapper and journal, mounts the actual answer component in headless Edge, routes browser requests through the real state handlers, edits controls, reloads and asks the model a follow-up. This does not exercise the desktop shell or the Next HTTP server.

Only `prompt` and `followup` reach the model as user text. `changes`, option-label patterns and `expected` are test metadata, not model hints. Numeric controls, keyboard-driven sliders, selects and checkboxes must match exactly one accessible control. Every edit must match the disk acknowledgement; report version 2 additionally records actual browser control values after reload and visible table text. Record version 1 only checked the disk reload state. An incomplete model turn cannot be reported as `workflow-completed`. Completion means the workflow ran, not that its formulas or explanation passed semantic review. Inspect the synthetic snapshots and responses against the preregistered expected values; independent reviews remain empty unless actually performed.

Each output directory is create-once and contains synthetic session/journal data, a report without hidden reasoning, a browser fixture and screenshots. Raw SDK sessions can include model reasoning and remain local. Reports record selected source digests, settings and scope; those hashes are not a complete dependency closure. Keep failures and prepare a new output directory after changes. Plan2 compiler 2.2 accepts scalar literal shorthand in atom positions, with original-plan admission before SDK coercion; Plan1 retains its original atom syntax. Keep prior compiler outputs and measurements unchanged.
