# Pi 1.0.2 native MCP adaptation

This continues draft PR142. It uses the public Pi native factories and `@earendil-works/pi-mcp` transports, with an explicit direct dependency pinned to 1.0.2. Next keeps that package external in both server compilation paths so native transport/error class identities stay shared with the external SDK. Pi owns protocol conversion, connection lifecycle, OAuth storage/refresh, resource conversion, progress, cancellation and reconnect semantics. Piora retains its extension load plan and `noExtensions:true`; it injects named replaceable MCP, codemode and tool-search factories only into normal, non-notes sessions. Codemode model helpers are disabled with `models:false`.

## Configuration and permission flow

Open a workspace, then Settings → Plugins → Pi native MCP. Connections start only after explicitly enabling native MCP and reloading a normal task. Saving configuration does not grant model access. The page exposes configured sources, project overrides, actual transport state/owner, exposure, discovered tools, resources, explicit sign-in/reconnect and registered-server connection approval. It does not present cached legacy metadata as a live native connection. Changed configuration immediately revokes execution; the page identifies an older live endpoint until reload. A real pending flag compares the configuration loaded by that session with the current merged files, integration enablement and registered-server approvals. Closing and reopening Settings retains the reload action while changes are pending; a successful reload clears it after configuration is loaded, independently of connection success. Existing credentials are omitted from API responses and the editor clears after saving a new definition. Config files use private atomic writes.

Native sources are exactly global `<agentDir>/mcp.json` and trusted project `.pi/mcp.json`, using strict JSON. `enabled:false` is the native disabling field. Project full definitions replace global definitions; partial project overrides may change only `enabled`, `exposure` and `toolExposure`, without copying global credentials. Project `auth.provider` is forbidden. Server names follow native Pi's ASCII namespace rules, with ambiguous hyphen/underscore namespaces rejected. Settings never grants project trust. Symbolic config files/parent directories and command evaluation in headers, environment values or OAuth secrets are rejected. Environment references (`$VAR` / `${VAR}`) and escaped dollars remain supported. Legacy adapter JSONC sources, SSE transport and cached metadata stay separate.

After connection, open Settings → Project tools to enable the desired tools and server resource access individually. The UI uses this existing project-wide entry point; the backend enforces the resulting permission policy separately in each session. The dormant session control is not mounted. `direct` tools can be declared immediately when authorized; `deferred` tools need authorized tool-search discovery; `codemode` tools are callable from an authorized codemode helper; `hidden` and withdrawn tools remain unavailable. Helpers cannot authorize other tools. All direct and nested calls pass the retained host capability hook, and native execution wrappers check again. Existing selected IDs survive delayed discovery, while new IDs start disabled. Project settings read already-discovered tools from private live sessions and never start a connection merely to inspect settings. Notes, device profiles, runtime ceilings and the existing definition budget remain enforced.

Resource helpers need both their own tool permission and a separate `mcp-resource:<server>` capability. Every request must name an authorized server. No-server aggregate listings and cross-server reads are blocked. An extension-registered server needs approval bound to workspace, name, registering source and full configuration; changing that identity requires a new approval. An installed extension owning `/mcp` can replace the native factory before any native connection; the page shows replacement ownership and disables native sign-in/reconnect controls.

## Verification and limits

Official `type:streamable-http` and `exposure:codemode-deferred` (including per-tool overrides) normalize to `http` and `codemode`. Login/reconnect requires an explicit currently authorized server; transport creation/start/send, bearer-token retrieval/refresh and HTTP reconnect fetches recheck live approval, enablement and configuration. Revocation disables UI management actions immediately while retaining local close/cancellation. Changed definitions require reload. Disabled integration or a registered server’s `enabled:false` takes precedence over `approval-required`; connection approval remains an independent field. Known configured credentials, bare bearer tokens, captured access tokens and URL query credentials are removed from incoming MCP payloads before conversion, logging or output-file persistence, and again from progress/results/rejected execution. Public error classes, numeric status/code and safe diagnostics remain, with separately sanitized cause/details/body/stack objects.

- HTTP 500, JSON-RPC error, progress, server logging, error-result and synchronous/rejected transport fixtures verify direct results, nested parent codemode output, all events, model-facing context and persisted transcripts do not contain known fixture credentials. Four revocation fixtures verify registered approval removal, disabled servers, changed endpoints and disabled integration produce no new transport/request/OAuth page; stale transport start/send fails and close remains usable.

- Real installed SDK sessions plus local stdio/Streamable HTTP fixture servers verify structured/image/error results, resources, four exposure modes, asynchronous restore, withdrawal, independent same-workspace permissions, direct/nested denial, parent call IDs, progress, Stop, explicit reconnect without replay, registered-server opt-in, config revocation, project ceilings and definition budgets.
- Loopback OAuth fixtures verify explicit RPC sign-in, authorization-code exchange, refresh, scope step-up, cancellation and redacted status/errors. No external account or live provider is used.
- API tests verify origin/content-type/workspace/trust enforcement, private configuration responses and non-copying project overrides. Browser tests verify the usable configuration controls and explicit actions. Actual Next dev home/settings pages were also checked through agent-browser, with no page errors or framework overlay.
- Packaging requires the official unbundled worker `@earendil-works/pi-codemode/dist/runtime/worker.js` and QuickJS WASM. An isolated production-closure probe asserts public factory/session exports, executes a real native local MCP tool through codemode/QuickJS, checks nested parent IDs and confirms `models` is absent. Piora's packaged API additionally verifies inactive native helpers and the native MCP command. CLI/RPC launchers, all 985 official source files and the strict embedded dependency checks remain verified.
