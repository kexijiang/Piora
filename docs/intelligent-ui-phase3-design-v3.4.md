# Intelligent UI 第三阶段方案 v3.4

2026-10-31 | 结合 OpenIntelligentUI 与当前 Piora 工作区重新设计 | 实施方案

## 1. 目标与这次调整

第三阶段让回答成为可以操作、保存并继续讨论的小工具。简单计算继续直接回答；比较、筛选和参数联动沿用组件；算法过程、空间操作、模拟和小游戏使用独立小程序。用户用自然语言提出任务，不必说出工具名或组件类型。

整体仍是三个阶段。本版替代 v3.3 作为后续实施依据，保留全部第三阶段目标及历史成果。新的重点是：**先验证真实模型能稳定生成有用的小程序，再逐项扩大能力；外观与完整使用流程一起交付。**

| 调整点 | v3.4 的决定 |
| --- | --- |
| 模块很多，但产品流程尚未证实 | 3B 设置真实聊天门槛，验证生成、操作、保存、刷新、追问和基本分支功能；注册了工具不等于已可用 |
| 创作契约长，容易重复纠错 | 共用形式选择策略；能力说明、示例、编译器使用同一版本来源；先用不同任务检验契约可学性 |
| 功能增加后样式容易退化 | 主题、字体、间距、控件和播放栏由宿主统一；在第一个完整流程中检查深浅色、字号和窄屏 |
| 复杂交互容易变成特例 | 以状态、事件、投影和渲染能力组合任务；扩展动态列表、拾取等通用能力，不按提示词识别某个演示 |
| 计划、实现、验证混在一起 | 分开记录已写代码、局部检查和完整应用证据；当前接入草稿继续验证，不外推历史测试结果 |

### 从 OpenIntelligentUI 借鉴什么

本地参考提交为 8391a94c1c3939c679e40ddd7bfc08a9ef690e70。采用其自由布局、共享设计系统、CSS 就绪后预览及受限宿主桥接的思路。参考项目的最终 iframe 可运行生成脚本，并注入库的 importmap；Piora 选择独立计算运行时，换取可暂停、可恢复和可核对的状态。[R1]

保留 Piora 的 AgentSession、Beta 开关、工具权限和持久化。参考项目单独调用 Jev 选择形式，其检查点存在进程内；这些不能直接替代 Piora 的会话与分支机制。[R2] 本轮不复制第三方代码；今后若复用 MIT 代码，按实际复制内容保留许可和归属。[R3]

## 2. 形式选择：先看任务，再看交互价值

由当前回答模型在同一轮结合用户目标、最近对话、已确认参数和可用能力作选择。共用一份语义策略，组件与小程序只补充各自契约。默认不增加每条消息必经的分类模型，也不按“预算”“表格”“模拟”等关键词触发。

| 用户表达 | 合适的处理 |
| --- | --- |
| “六个人分 480 块，每人多少？” | 文字回答 80 元；没有反复操作的必要 |
| “人数还没定，我想改着看看。” | 组件，复用已知总额，让人数与结果联动 |
| “这个排序我没看懂，能一步步点着看吗？” | 小程序，用单步、过程高亮和解释呈现变化 |
| “这个三角形拖一拖，面积会怎么变？” | 小程序，空间操作与面积来自同一状态 |
| “提成比例还没定，先给我算出来。” | 先澄清；做成输入框不能让缺失的规则变成事实 |
| “为什么刚才那个结果变了？” | 读取已确认状态解释，不自动新建或重生成 |

### 实现方法

- 公共策略回答五件事：目的是什么、事实是否足够、交互是否有收益、现有能力能否满足、是否已有可继续使用的输出。
- 保留组件工具 piora_render_ui_plan；小程序使用 piora_render_mini_app。工具可用性同时取决于 Beta、会话加载状态和已验证的运行能力。
- 能力目录区分“计划支持”“代码已接入”“验证后可开放”。提示只公布实际可用的能力；无法完成时说明缺口，不能悄悄把任务换成一个近似演示。
- 同一任务修订沿用稳定输出身份。跨组件与小程序切换也要说明状态处理，不通过换工具绕过修订确认。

程序只核对结构、资源、来源和权限；是否应该用 UI、业务规则是否正确仍需语义与任务结果验证。文字和澄清样本在评估中保留，漏调用不能被排除出统计。

### 生成失败如何处理

原始参数先校验，再编译和隔离试运行。返回字段路径、稳定错误码和可修复原因；只展开无歧义简写，不猜测公式、单位和事实。沿用同一 PromptRun 的 3 次接纳尝试、1 次模型纠错、首次尝试起 60 秒窗口，两个工具及模型恢复共用预算。超过预算保留旧结果并解释，不无限重试。

真实模型开发样本会分别记录“没选对形式”“没写对契约”“运行失败”“任务结果错误”。先定位原因再改策略；窗口与预算是待验证的初始值，不能靠放宽预算掩盖契约问题。

## 3. 创作自由与宿主责任

采用 **HTML/CSS 布局 + 普通 JavaScript 计算 + 可信渲染器 + 独立状态**。模型决定任务内容与布局，宿主承担主题、依赖、计时、资源限制、保存与动作权限。已有八类组件继续适合简单任务，小程序表达不受这八类组件限制。

```text
AgentSession -> 形式选择 -> MiniAppPlan -> 编译 / 试运行 / 发布
                                      |
                                 MiniAppHost
                           /                 \
             文档 / SVG / Canvas / 3D     Worker + QuickJS
                  可信渲染器              显式状态与计算
                           \                 /
                          版本化事件与投影帧
                                  |
                    独立状态存储 / 追问 / 登记动作
```

| 模型提供 | 宿主保证 |
| --- | --- |
| 用途、假设、输入含义及初值 | 缺失业务事实不自动补齐；保留用户给定的值 |
| 有界 JSON 状态结构 | 检查每次转换及保存，绑定运行版本与来源 |
| HTML/CSS、SVG 绑定和视口 | 编译为允许的节点与样式；图形由固定渲染器绘制 |
| init、reduce、advance、project | 初始化、事件处理、固定时间步、同一状态的结果投影 |

计算程序可用普通函数、循环和数组，运行在 Worker 内的 QuickJS/WASM；不能直接读写 DOM、网络、文件或 Electron。project 只读取，不推进模拟；图形、数字与解释由同次投影产生。随机种子、逻辑时钟和交互状态显式保存，不依赖闭包或浏览器计时器恢复进度。

### 控制契约复杂度

从一份版本化能力定义生成 schema、短说明与可执行示例，验证示例覆盖实际解析规则。核心协议保持稳定，动态列表和三维事件以能力版本扩展。不要为每个业务公式再创造一套表达式语言；也不承诺能直接运行网上任意 HTML/JS 或完整 Three.js 示例。

这一选择需要更多渲染适配工作，但能复用现有状态基础。直接运行 iframe JavaScript 更自由，却无法仅靠 DOM 快照保存其闭包、定时器和游戏进度；整体引入 CopilotKit 后端则重复已有会话体系。后续只在真实任务暴露能力缺口时扩展契约。

## 4. 复杂任务按通用能力实现

| 能力 | 设计与完成证据 |
| --- | --- |
| 算法演示 | state 保存序列、当前步骤和高亮；单步与播放共用逻辑。核对过程、元素不丢失、终态，不只看最终排序 |
| 几何拖动 | 宿主统一坐标转换、指针捕获和释放；程序更新点位。面积、图形和说明同步；数值输入或键盘可替代拖动 |
| 动态列表 | 有限重复模板、稳定 key、行身份与字段绑定；展开后计入节点预算。验证增删、重排后事件仍作用于正确项目 |
| 模拟与持续小游戏 | 固定时间步、显式随机源、按键与碰撞状态；支持暂停、单步、复位和终态。固定输入可回放，长时间运行不累积隐藏状态 |
| 三维拾取与相机 | 固定渲染器返回对象 ID 和有限坐标，事件绑定显示帧；视角、缩放与选择进入检查点，恢复时重现 |
| 三维关系教学 | 用几何状态驱动展开、旋转和标签；独立核对邻接、边长、重叠与还原。能画立方体不足以证明教学任务完成 |

### 先把事件时序做正确

事件带实例 epoch、视口与显示帧身份。连续移动可合并，按下、松开、取消、点击必须保持顺序。保存前先冻结新输入，排空已接收事件再取检查点。三维精确拾取优先在暂停或静止场景完成；过期帧事件拒绝，不能落到错误对象上。

页面隐藏、失焦、停止与卸载都要处理按键和拖动释放，避免恢复后仍在移动。默认暂停，同一聊天视图只允许一个实例持续播放。停止终止计算并释放 GPU；强制终止只能恢复最近确认的检查点。

### 资源限制与能力声明

现有原型采用单步 8 ms、30 fps、堆 32 MiB、400 个文档节点、200 个网格等初始上限；还需分别约束消息、绘图命令和三角形。目标设备校准前，这些是配置值，不是性能测量。超预算暂停并保留最近状态，不能丢逻辑步来伪造实时性。

3B 先以离散过程和二维空间操作验证核心契约；3D 再接通上述完整复杂能力。先后顺序不缩减第三阶段范围。每项新增能力必须同时有编译规则、运行支持、可执行说明、任务正确性检查和桌面证据，才能向模型宣称可用。

## 5. 保存、追问和修订是一条流程

发布记录不可变，保存程序、计划摘要和工具来源；交互状态独立保存 inputs、state、rng、tick、运行版本、投影结果及 stateRevision。用户操作不改写原始工具回执，也不把小程序状态机放入普通聊天组件。

```text
暂停并冻结输入 -> 排空输入与 Worker 队列 -> 取得一致检查点
  -> IndexedDB 持久草稿 -> 校验分支与 expectedRevision
  -> 服务端重新 project、原子保存 -> 返回幂等回执
  -> 本轮追问读取已确认参数、假设和结果
```

| 场景 | 必须满足的行为 |
| --- | --- |
| 保存失败或响应丢失 | 草稿保留；查询同一 requestId 回执，重试沿用身份。只有确认保存后才清除对应草稿 |
| 保存期间继续操作 | 新修改排在前一回执之后，不覆盖已经发出的快照；旧请求返回不得清除更新的草稿 |
| 多窗口、旧分支与旧草稿 | 使用版本比较与来源分支祖先校验；冲突保留双方，由用户决定，不能静默后写覆盖 |
| fork、复制与导出 | 继承保留历史可见的已确认状态，后续独立写入；导出静态参数、结果和来源，不执行生成程序 |
| 删除与恢复 | 发布、状态及相关侧文件随会话处理；未确认本机草稿明确提示和保留，不伪装成已保存 |
| 关闭 Beta 后重新开启 | 停止实例，撤销旧生成和保存请求；旧请求即使迟到也不得提交。已确认结果和恢复草稿保留 |

### 程序修订与状态迁移

新程序先成为候选，旧版本继续可用。按字段含义、单位和约束判断输入兼容性，兼容输入可预填；内部运行 state 默认重新 init。确需迁移时，使用单独受限转换，重新校验与投影，展示前后变化后由用户确认。失败保留旧程序、旧参数与草稿。候选发布前再核对来源版本，避免用户修改期间被旧候选覆盖。

### 动作和继续提问

外部动作复用已登记入口，由宿主按钮发起；先保存当前结果，再按现有权限检查目标与操作。iframe 事件不是授权，加载和计时器也不能自动发消息。“按当前结果继续问”走同一保存流程；保存失败时由用户重试或明确使用已保存状态，不能默默采用旧值。

## 6. 外观从第一条完整流程开始统一

宿主提供主题、字体、间距、输入外观、边框、焦点和状态提示；模型负责内容层级、列布局与任务图形。让不同任务有不同交互形式，同时保持 Piora 的视觉习惯。不要把“支持自由布局”变成每次生成另一套应用样式。

| 交互目的 | 默认设计 |
| --- | --- |
| 精确输入或录入 | 数字框、文本框；保留单位、约束和错误说明 |
| 少量明确选项 | 选择器或分段按钮，不强制变成连续滑块 |
| 连续探索 | 滑块配合当前值和精确输入；只有范围本身有意义时使用 |
| 过程与时间 | 播放、暂停、单步、复位；按钮顺序及状态由宿主统一 |
| 空间关系 | 拖动、选择、旋转，同时提供键盘或数值替代 |
| 结果与解释 | 摘要、指标、图形和详细说明分层；不要把动态结论写死在标题中 |

### 预览与正式界面

参考 CSS-first：样式及必要布局依赖闭合后才展示只读预览，避免先出现无样式大表格。增量更新复用现有框架，不在每个片段重建界面。预览不执行模型程序，不接受操作；三维使用占位，不提前分配 GPU。试运行通过且发布确认后再进入正式交互状态。

主题与字号以宿主消息同步到隔离视图；HTML/SVG 使用受控 token，Canvas/3D 使用语义色板及标签映射。切换主题或字号不重置任务状态。系统减少动画偏好影响自动播放和过渡；窄屏可重排，键盘焦点清晰。

### 保持模块独立

公共 answer-output 层只负责能力目录、生成生命周期、预览、渲染和保存门禁。intelligent-ui 与 mini-app 作为独立适配器管理各自协议和状态；ChatWindow、MessageView、useAgentSession 只调用公共接口。

Beta 关闭时不加载交互 Surface、QuickJS 或 Three.js，历史显示文字快照；服务端依旧复核开关、分支、版本和来源。依赖随应用固定分发，开发桌面与发布包资源路径分别验证。

3B 的视觉门槛至少覆盖当前主题、深浅色切换、用户字号和窄屏；3D 完成图形语义色、全部复杂交互及无障碍组合验证。已经出现过的样式退化不能留到全部能力做完后才处理。

## 7. 实施顺序与当前状态

3A 至 3E 是第三阶段内部步骤。现在优先补齐 3B 的真实产品闭环，已有状态与继承模块继续复用。先用小范围真实模型暴露契约问题，再扩展复杂能力；每步输出 Markdown 成果报告和 PDF。

| 步骤 | 交付及进入下一步的条件 |
| --- | --- |
| 3A 基础契约 | 核对已有编译、隔离计算、渲染、停止和资源准备；最小计划实际执行，旧组件相关回归成立 |
| 3B 完整产品闭环 | 接通共同策略、工具、生成适配、预览及正式界面；真实开发桌面完成生成、操作、保存、刷新、追问，以及基本 fork/复制/静态导出/回收站；做首批 V4.1 与视觉检查 |
| 3C 恢复与修订动作 | 完整多窗口、断网、取消、草稿分页、Beta 开关时序、迁移确认及登记动作；失败可恢复，回执与来源正确 |
| 3D 复杂能力与泛化 | 动态列表、拾取、相机、模拟、持续小游戏及三维教学；完成主题、无障碍、性能、自然语言开发集与独立任务核对 |
| 3E 综合验收 | 三阶段开发完成后运行完整 CI、封存集和人工语义验收，审计未覆盖项并输出总报告；发布按既定流程另行执行 |

### 首批真实模型怎样测

使用用户指定的 DeepSeek V4.1，先做 8 个开发任务，各 3 次：两例文字/澄清、两例组件、四例小程序，覆盖离散过程、二维拖动、自定义计算与多轮解释。这些计入完整开发集，不作为独立的“全部通过”捷径。

既观察首次可运行率，也实际操作并核对结果。错误任务即使能渲染也算失败；多次修复才成功必须记录修复次数。若关键失败来自协议或形式选择，先修这些问题，再推进更多渲染能力。

### 本轮源码核对的事实

Piora HEAD 为 b41fa2ff，专用分支 codex/intelligent-ui，包含未提交修改。编译器、Worker、状态服务、IndexedDB 草稿、Surface 与基本继承已有局部验证报告。当前源码也已出现小程序扩展、catalog/renderer 注册、生成适配、共同决策策略及 Beta 取消草稿；旧进展中“尚未注册”的描述需要更新。

这些接入修改尚无本轮完整聊天、真实模型或桌面证据。此前 62/62、90/90 等是各自报告对应快照，不覆盖之后的所有改动。本次只修订方案、状态说明和文档索引，导出并检查 PDF；未增加产品功能或重跑代码测试，也未提交、推送或运行 CI。

## 8. 可行性、验证与依据

可行性判断：现有原型足以支持继续接入，主要不确定性是模型遵守契约的稳定性、复杂任务的正确性和真实桌面表现。独立计算有利于恢复和核对，但增加渲染适配成本；共享设计系统改善一致性，不能代替任务正确性检查。

| 风险 | 验证及处理 |
| --- | --- |
| 契约太长或工具选择不稳定 | 首批 V4.1 实测提前到 3B；区分选错形式、参数错误、运行错误和结果错误，再调整共同策略与可执行样例 |

### 完整评估保持原定范围

48 个初始任务：16 小程序、12 组件、12 文字、4 澄清、4 能力缺口；按任务族划分 32 开发、16 封存，每例 3 次。封存样本留到综合验收，泄露到调试后转为开发样本并补新样本。允许多种合理形式的任务预先标注。

测试只用 DeepSeek V4.1；运行前核对配置及可获得的实际返回标识，别名不能自行当作版本证明。无法确认时记录为模型身份待核实，不静默改用 V4 Pro。保留任务、策略、能力版本、耗时、原始失败及修复过程；超时、漏调用和取消分别报告，不删分母。

记录形式选择、首次成功、预算内成功、任务正确性、保存与分支一致性，以及真实设备响应和资源趋势。数值质量门槛在开发集基线后、封存评估前固定；静默丢失、越权和错误版本覆盖属于阻断缺陷。人工语义验收与完整 CI 仍按用户安排放在三个阶段开发完成后。
