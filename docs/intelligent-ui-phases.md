### 为什么此前也提到两个阶段

Issue #235 按产品范围分为两大阶段：第一大阶段是可信组件交互，第二大阶段是模拟与小游戏。实施方案按交付工作分为三个阶段，其中交付阶段 1 和 2 对应产品第一大阶段，交付阶段 3 对应产品第二大阶段。

### 完成状态的准确含义

前文“第一阶段已实现”指核心实现范围已落地，不代表 Issue #235 的第一大阶段全部验收通过。当前已交付可交互的实现；真实模型验证、操作按钮、参数增量渲染和发行验收仍有明确缺口。

当前工作分支 codex/intelligent-ui 已同步 upstream/main 的 ba8d2022（beta.44）；最初实现基线为 37959a18。功能仍是未提交的工作树修改。本轮补齐运行中引导、排队和队列提升前的保存与取消检查。

## 阶段 1 基础能力与技术验证成果

状态：核心实现和本地验证已完成，阶段验收待完成。目标是打通“生成 → 本地操作 → 参数保存 → 继续追问”，并使实验功能可以独立启停。

| 成果 | 已落地行为 |
| --- | --- |
| 实验功能入口 | 设置中增加 Beta Features / 实验功能，Intelligent UI 默认关闭并持久保存选择。 |
| 可信界面组合 | 提供 text、number、slider、select、checkbox、metric、table、barChart 八种节点；支持受限算术、条件与比较表达式。 |
| 即时交互 | 滑块及输入改变在本地重算，不为每次调整请求模型；每次工具提交完整且校验后的规格，可在最终文字回答前操作。 |
| 保存与追问 | 服务端保存参数，本机保留未确认修改；普通输入和运行中追问等待保存，失败时保留输入并提示。 |
| 历史与分支 | 覆盖刷新、虚拟列表卸载、祖先修改、兄弟分支、fork、复制、HTML 快照导出及回收站生命周期。 |
| 稳定性修复 | 历史补齐不重挂载焦点控件；等待保存期间停止、撤回、切换聊天或新一轮会取消旧提交。 |

### 模块边界与开关语义

聊天公共层只识别 answerOutput 内容封套、文字快照及通用保存接口。规格、计算、状态与渲染位于独立模块，并按需加载；继续复用原有 AgentSession、消息通道与工具权限。

关闭开关时，前端立即切换为文字快照；Agent 能力在下一轮生效，正在运行的一轮保持原能力。已保存状态继续保留，关闭前未保存成功时可明确选择保留本机草稿。

### 当前实现边界

尚无工具参数 token 级局部节点渲染，也没有新的 UI 业务动作执行接口。参数修改只保存数据；文件、网络等真实操作仍通过普通对话工具执行。当前协议不执行任意 HTML、JavaScript 或 URL。

## 阶段 1 手工验收快速上手

请在本次专用工作树 codex/intelligent-ui 中启动开发服务。安装版本不会自动包含这些未提交功能；测试入口为 http://127.0.0.1:30145。完整场景见 docs/intelligent-ui-testing.md。

### 启动与开关

依次运行：node scripts/prepare-development.mjs；node node_modules/next/dist/bin/next dev -H 127.0.0.1 -p 30145 --turbopack。等待就绪后打开测试地址。测试结束在该终端按 Ctrl+C。不要运行 next build 或本地发布打包。

打开设置 → 实验功能（Beta Features）→ Intelligent UI。新建测试对话，选择已经配置、支持工具调用的模型。正在执行的一轮保持原能力，开关从下一轮模型请求生效。

### 可复制的基础提示词

请调用 piora_render_ui 生成聚餐采购清单，不要只给 Markdown。人数用滑块，默认 4、范围 1 到 20；每人份数用数字输入，默认 2；每份单价用数字输入，默认 12 元。展示总份数、总价和采购表。总份数 = 人数 × 每人份数，总价 = 总份数 × 单价；结果必须使用本地计算表达式，随控件变化。不要添加下单或网络操作按钮。

### 逐步验收

| 操作 | 应看到的结果 |
| --- | --- |
| 生成默认界面 | 4 人 × 2 份，共 8 份、96 元，出现可操作的控件。 |
| 人数改为 8 | 立即变为 16 份、192 元；调整本身不触发新一轮模型生成。 |
| 等到已保存，再刷新 | 恢复人数 8、每人 2 份、单价 12 元及总价 192 元。 |
| 追问当前人数和总价 | 模型应按当前保存值回答 8 人、192 元，不回到初始值。 |
| 关闭后重新开启 | 关闭时显示文字快照；重开后恢复已保存参数。 |

进阶验收包括：运行中引导与排队先保存参数、取消后原消息与新草稿都可恢复、fork 和历史分支互不污染。每项分别标记通过、失败或未覆盖，并记录模型、复现步骤和界面保存状态。真实模型验收目前仍待完成。

## 2026-10-29 用户实测反馈与第二阶段调整

用户已进行第一阶段实测，使用口语化请求时，Intelligent UI 可能生成失败，也可能经过多次重试才能生成。用户同意将这一问题放入第二阶段优化，并明确要求注意泛化性。此记录确认用户已做实测，不将其扩大为全部验收项通过；尚未取得逐次日志、具体模型及成功率，根因待排查。

### 第二阶段优先工作

1. 建立自然语言请求的失败基线。区分未选择工具、工具参数或协议不合法、表达式与引用错误、渲染或保存失败、供应商与网络故障；从实际失败证据确定改进位置。不能仅凭多次重试就判断是模型能力或提示词问题。
2. 改善任务到界面的选择与生成。用户描述目标即可使用，不要求工具名、组件名或计算协议；根据输入、结果、交互需求选择控件和布局。信息不足时简短澄清或明确默认值；简单问题仍允许直接回答。
3. 降低生成协议的出错成本。评估简化工具说明和结构、提供可复用的组件组合与准确的校验反馈；修复应保持任务语义、用户输入及既有状态，不能通过放宽校验或删除关键结果提高表面成功率。
4. 增加有边界的修复与降级。按错误类型处理，限制自动修复次数和耗时；重复失败时给出可理解原因及可用替代，不进入无限重试，也不把文字降级计作交互界面成功。具体预算在基线测量后、正式验收前固定。
5. 继续完成组件与布局扩展、参数增量渲染、受控动作及桌面发行验收。首先解决自然语言下的稳定生成，不能用增加组件数量代替成功率验证。

### Intelligent UI 触发决策（2026-10-29 补充）

用户进一步强调“什么时候应该使用 Intelligent UI”是关键能力，作为第二阶段独立任务和验收维度。

- 根据用户意图、交互收益、信息是否充分及现有能力选择回答形式。优先用于用户需要反复调参、切换条件、比较方案、筛选数据或配置选项的任务；明确要求可操作界面时，在能力范围内应生成。
- 一次性计算、事实问答、概念解释、文字创作和只需展示结果的静态表格，通常直接文字回答即可。出现“预算”“计划”“表格”等词本身不足以触发。
- 对复杂但没有明确交互收益的请求，不把复杂程度当作生成 UI 的理由。可先给简明答案并在确有收益时提供交互选项；缺少关键信息且会改变任务结果时才澄清，避免每次都询问是否生成。
- 考虑当前协议是否能正确表达任务、数据是否具备、生成成本是否值得；能力不足时说明边界并提供替代，不生成装饰性控件，不通过随意假设掩盖信息缺口。后续受控操作仍遵守原权限，界面触发不代表动作授权。
- 随对话变化重新判断：同一任务初次可能只需文字，用户开始比较不同条件时再进入交互。已有界面可以更新或解释时，避免重复生成；尊重用户“只要文字”“不要交互”的选择。

配对验收例：“680 元六个人平摊，每人多少”倾向直接回答；“人数和费用还会变，做个能随时调整的分账表”应生成交互。“列一下两个方案的优缺点”不强制生成界面；“让我换人数和服务选项，看看两个方案的价格怎么变”适合交互。对这些例子进行自然改写，并扩展到未参与调优的领域，验证意图判断而非关键词匹配。

验收把“触发选择正确”和“触发后的生成成功”分开统计：记录适合交互任务的漏触发、不适合任务的误触发，以及澄清是否必要。不能靠一律生成提高工具调用率，也不能靠一律文字降低失败率。可接受多种回答形式的模糊任务单独标记并人工复核；评估首次完整任务结果与用户操作成本，不以调用次数作为质量指标。实现方式在基线分析后确定，不预先要求增加一次独立模型请求。

### 泛化与验收方法

- 保留详细协议提示作为组件测试，另建不出现工具名、组件类型或表达式语法的自然语言任务集。
- 覆盖计算、比较、条件清单、配置表单、数据展示等不同任务，以及无需界面、能力范围外、条件缺失的请求。包含口语、省略、换说法、改单位、多轮修改和更正需求。
- 开发示例与验收任务按任务类别隔离；保留未参与提示词调整的新领域、新组合及自然改写。不能仅对原采购、分账等示例换数字来证明泛化。
- 同一组任务在选定的不同模型上重复测试，分别记录首次可用率、有限修复后的成功率、修复次数、耗时、降级率及不必要生成界面的比例。按任务类别和模型列结果，避免只报告总体均值或挑选成功案例。
- “可用”同时要求需求满足、控件适当、计算正确、交互联动一致以及保存/刷新/追问可继续；通过 schema 校验不等于完成任务。模型和网络失败分别统计，端到端体验仍计入用户等待与失败。
- 先采集改进前基线，再锁定目标、重试预算和验收集，用同一条件复测；记录新场景是否改善及普通文字回答是否退化。当前尚未测得这些指标，不承诺已达成数值目标。

以上为设计调整时记录的反馈及阶段任务；后续实现进展单独记录，避免将历史验收结果扩大为当前实现通过。第三阶段仍为隔离小程序、复杂模拟与小游戏，依赖第二阶段的稳定生成和权限边界。后续阶段成果报告及 PDF 纳入基线和实际结果，保留已有 PDF 的历史版本。
