# Intelligent UI 第二阶段成果

v2.12 · 2026-10-30 · 嵌套计算规范化与开发集复测。第二阶段仍在开发，尚未完成产品验收。按用户要求，三个阶段功能开发后统一处理 CI。

## 1 本轮实现与本地验证

Plan2 编译器升级为 2.4：支持模型直接在计算参数、指标、表格单元格和柱状图数值中写出受限的嵌套计算。宿主将其转换为已有的命名计算结构，再由原有编译器检查引用、类型、循环、默认数值和展开成本。它只规范化无歧义的表达，不补猜缺失业务规则、变量或计算公式。

例如“人数 ×（餐费 + 门票）”可以直接表达两层运算，不必要求模型先为加法结果另起一个名称。原来的命名计算仍可用，重复计算应继续复用名称。Plan1 的输入格式不变。

### 校验与预览边界

- 嵌套运算只能包含 op 和 args，仍使用原有九种受限运算；带额外 id、占位字段、字符串算术或未定义引用的输入继续拒绝。
- 命名与嵌套运算共用最多 256 项计算、表达式深度 12、展开节点 4096 和完整计划 64000 字符限制。布局、动作等非表达式位置保留原 JSON 深度限制。
- 内部名称避开原始输入中的所有字符串，避免碰巧补上缺失引用或覆盖用户名称。错误路径映射回模型实际提交的位置，不要求模型理解内部转换名称。
- 增量预览和完整编译共用同一转换。模型端 schema 保持有限大小；嵌套参数的完整约束由 SDK 类型转换前的原始参数验证强制执行，不以宽松的深层 schema 代替校验。

## 2 原始开发集复测

复用原 40 个开发任务，每任务每模型运行三次，使用 DeepSeek Flash 与 V4 Pro，共 240 次。当前配置为 intent-4、Plan2 2.4、low reasoning、6000 输出 token、每轮最多四次模型请求、供应商重试为零、任务期限 120 秒。

生成工具实际经过应用接纳绑定和 SDK runToolCall，原始参数校验失败也会计数；同一合成用户回合最多三次接纳、一次纠错，从首次 UI 尝试开始的活动窗口为 60 秒。成功结构仅保存在评估内存中，不标记为磁盘提交。

两模型各完成 120 次对话流程，无供应商错误或超时。完成对话不等于成功生成 UI：Pro 仍有一次文字降级，保留为 UI 失败。

| 观察值 | Flash | V4 Pro |
| --- | --- | --- |
| 完成且首次结构有效 | 58/60（96.7%） | 59/60（98.3%） |
| 预算内完成且最终结构有效 | 60/60（100%） | 59/60（98.3%） |
| 首次数值轨迹匹配 | 58/60 | 59/60 |
| 最终数值轨迹匹配 | 60/60 | 59/60 |
| 应交互却没有 UI 尝试 | 0/60 | 0/60 |
| 文字回合中尝试 UI | 0/48 | 0/48 |
| 澄清回合中尝试 UI | 0/9 | 0/9 |
| 能力范围外回合中尝试 UI | 1/9 | 0/9 |
| 应交互任务中多次尝试 | 4/60 | 1/60 |
| UI 任务耗时 P95，含失败惩罚 | 10.16 秒 | 21.81 秒 |

Flash 的四次多调用中，两次是格式纠错，另外两次先后生成了有效版本，不全是失败重试。Pro 的失败起于空参数触发不可修复的版本错误，后续调用被拒绝，最终明确改用文字；没有绕过预算或将文字计作 UI 成功。

每模型的六项前向技术开发目标均达到，目标文件未修改。耗时采用最近秩 P95，未成功生成 UI 的任务至少按 120 秒计入，包括正常结束但退回文字的任务。报告脚本初稿遗漏后一种计费，已修正并保留初稿，Pro P95 从 21.46 秒修正为 21.81 秒；原始模型运行没有重写。

独立数值核对沿同一表达式改变输入；只证明这些轨迹，不证明所有业务语义或真实保存。脚本核对两组模型设置、编译与策略依赖哈希一致，并验证完整冻结记录。逐任务结果与文件哈希见 intelligent-ui-phase2-inline-2026-10-30.json；原始材料位于 .verification/intelligent-ui-development-admitted-2.4。

## 3 Review、剩余问题与试用

本轮自查重点是无歧义转换是否改变含义、是否突破计算预算、预览与最终编译是否一致，以及真实 SDK 是否仍能拦截深层无效参数。本地测试覆盖惰性条件分支、内部名称碰撞、缺失引用、循环、复杂度上限、逐字符预览和原始参数接纳。未执行新的独立审查，不能据此声称独立 Review 通过。

### 已知边界

首次结构有效、变参数值匹配和用户任务可用是三个不同结论。开发集已参与调优；两模型顺序采样及供应商波动限制比较解释，不能用这组数据宣称泛化或因果改善。旧 2.3 大样本未使用当前真实接纳路径，也不能直接当作同条件对照。

Flash 在一个要求小球弹跳动画的任务中尝试生成不等价的计算面板，调用被拒后退回文字；这仍是能力范围外的错误尝试。另一个房租澄清回答先说“三个人平分已经明确”，随后又问分摊规则，与用户“分法不一样、尚未确定”矛盾。只是不调用 UI，并不代表问对了问题；静态标题和说明在改参后是否仍准确，也需语义检查。

当前尚未完成封存任务复测、独立人工语义评判和完整桌面动作矩阵。原有 2A 至 2D 功能与兼容路径继续保留；本轮没有增加任意代码执行能力。CI 与跨平台发行检查依用户安排后置，不阻塞阶段间开发推进。

### 用口语化请求试用

- “四个人出去玩，每人餐费 20、门票 10，弄个能改人数的小工具。”初始 120 元；人数改为 6，应为 180 元。保存后刷新，再问“现在总共多少”，应沿用当前参数。
- “房租 6000，三个人按 1:2:3 分，租金让我改着看。”初始 1000、2000、3000；租金改为 9000，应为 1500、3000、4500。
- “我们公司的提成分档，但档位还没告诉你，帮我算卖十万拿多少。”应先问分档规则，不能自行填费率生成工具。
- “预算 9000，花了 6800，还剩多少？”应直接回答 2200。
