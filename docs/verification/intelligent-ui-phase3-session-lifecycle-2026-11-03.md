本批从已有独立状态能力继续推进复制、分叉、导出与回收站组合。检查发现消息内分叉已经等待交互状态保存，侧栏复制和历史 HTML 导出却直接请求服务端；移入回收站也未等待已打开子会话的待保存状态。这些入口可能使用较旧的确认快照。

## 保存成为共同前置条件

复制任务先通过公共输出接口等待源会话保存，再请求服务器复制；失败显示原因，阻止复制，保留原草稿。相同任务正在复制时不重复发起请求。HTML、原始 JSON 和 Markdown 下载也先等待当前会话的挂载输出保存；只有 HTML 附带已保存的交互状态，其他格式继续保留原有导出含义。

移入回收站先保存用户已确认删除范围内的挂载会话，包括子会话；任一保存失败就不发起删除。未选中的会话不会因此被保存或阻塞操作。其他窗口的独立草稿仍受既有冲突和恢复规则约束，本次没有跨进程收集或自动合并草稿。

这些入口使用通用输出接口，没有让侧栏或历史界面依赖小程序计算与渲染实现。服务端来源、版本和分支校验保持不变，不自动覆盖冲突版本。

## 桌面复测发现的并发问题

真实桌面中，在追问显示后立即编辑并保存，状态刷新与保存可能同时取得控制器检查点锁，引起 BUSY 并停止交互。新增受控网络等待的浏览器回归先复现失败；状态客户端让刷新与保存等待彼此完成，同一轮开始也不会跳过必要的对话边界刷新。

这里修复的是同一客户端的检查点操作重叠。未确认草稿仍保留原分支身份；真正切换分支或其他写入冲突继续拒绝，不把新旧分支强行合并。最新桌面复测仍遇到追问后编辑返回 409，说明上述定向修复没有解决整个时序问题；不能宣称追问后的继续编辑已经完整修复。

另一轮桌面运行发现 HTML 导出返回 500，错误为动态导入表达式过于复杂。SDK 导出器依赖安装目录内的模板，现已保留原生文件 URL 导入，避免 Next 打包器替换为动态上下文。SDK 只读导出回归通过；修改后的真实桌面运行提前在保存处失败，因此实际下载仍未复测通过。
