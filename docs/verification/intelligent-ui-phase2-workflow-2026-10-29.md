# Intelligent UI 连续工作流成果

2026-10-29 · v2.8 · 第二阶段实施增量，尚未完成整体验收或发布。

## 1 根据真实失败改进协议

本轮把自然语言生成、生产 SDK 与发布记录、浏览器修改、磁盘保存、刷新和继续追问连成了一条可重复验证的流程。测试使用隔离的合成会话，只启用 UI 生成工具；浏览器挂载真实回答组件，并调用真实参数路由处理函数。未经过 Next HTTP 服务或 Electron 桌面外壳。

### 发现的问题

Pro 模型生成课程筛选器时，第一次将表格写成普通字符串与数字。旧 Plan2 要求每个单元格都包装为 literal 对象，结果被拒绝，模型再用相同课程数据补齐包装才成功。首次生成及纠错共约 58.7 秒，说明结构正确性问题会直接影响等待体验。

### 已实现的改进

Plan2 编译器升级为 2.2.0，允许在表格单元格、指标、图表值和派生计算参数中使用字符串、有限数字和布尔值简写。它们与 literal 对象完全等价。引用仍明确写为 input 或 derived 对象；数字形状的字符串仍是文字，不执行公式、不推测字段名，也不补造业务数据。Plan1 的语法和已保存 Surface 协议保持不变。

SDK 会对不合规范的参数进行自动转换，例如把 null 变成文字。现在原始计划先通过有界编译校验，再进入 SDK 校验；缺失值、错误类型、非法引用及资源超限不能借转换绕过检查。失败仍消耗同一运行预算，保留一次纠错及不可修复诊断。流式预览和最终编译使用相同的简写解释。

测试脚本也补齐了实际控件核对：数字输入、滑块键盘操作、下拉选择和勾选都从浏览器操作；每次保存核对磁盘值，刷新后再读取 DOM 控件。模型未正常结束时记录失败，不把已保存界面当成整个流程成功。

## 2 真实模型与浏览器结果

修改前使用 DeepSeek Flash、DeepSeek V4 Pro 分别运行出游分摊、聚会采购、课程筛选，共 6 个开发流程。每个流程独立会话、一轮生成、若干次浏览器修改和一次追问。修改后对两个模型各复测一次课程筛选，共 8 个流程、16 个用户轮次。均使用 low thinking、6000 输出 token 上限、供应商重试 0、每轮 120 秒上限；生产 UI 尝试预算继续生效。

| 场景 | 浏览器操作与独立预期 | 实际观察 |
| --- | --- | --- |
| 出游分摊，两模型 | 4 人改 6 人，餐费 40 改 50 | 总额依次 400、540、600；最终每人 100，追问读取 6 人与餐费 50 |
| 聚会采购，两模型 | 饮料 12 箱改 8 箱，零食 20 包改 30 包 | 总价依次 1024、736、816；追问使用保存后的数量 |
| 课程筛选，两模型 | 全部改运动，上限 200 改 100，再改文艺 | 依次显示 4 门、篮球与羽毛球、仅篮球、仅摄影；原始 4 行仍保留 |
| 简写改进后课程复测 | 两模型重复上述筛选与追问 | 均一次工具调用完成；最后只显示摄影，追问不重新生成 |

修改前 6 个流程有 5 个首次结构有效，Pro 课程流程纠错一次后完成。修改后的两个课程样本均一次调用成功；生成轮耗时分别约 8.1 秒与 39.3 秒。样本和运行时间不足以证明总体成功率或延迟提升，不能作性能对照实验结论。

8 个流程均完成保存和后续追问，追问均未重新调用 UI。最早两个报告仅核对刷新前后的磁盘状态；后续 6 个报告另外明确核对刷新后的浏览器控件值。课程样本同时检查浏览器实际可见行，不能把保留在磁盘的完整表格当成筛选结果。

### 仍保留的语义缺口

Pro 采购追问给出 8 箱和正确费用，但未列开发预期中的 192 瓶；Flash 出游生成了未明确要求的整数餐费步长及金额舍入。已有静态说明在参数改变后可能失真的风险，也不能据此次样本未复现就认定解决。本次没有独立人工双评，也没有使用封存集输出调优；不记为完整泛化验收通过。
