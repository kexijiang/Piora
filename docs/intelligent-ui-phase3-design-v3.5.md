# Intelligent UI 第三阶段方案 v3.5

2026-10-31 | 结合 OpenIntelligentUI 与现有实现重新设计 | 后续实施依据

## 1. 产品目标与主要调整

第三阶段让 Piora 根据任务生成可以操作、保存和继续讨论的小工具。用户说“这个过程能一步步看吗”“拖一下会怎样”，模型选择合适的表现形式；用户不必指定工具名，也不必描述界面结构。整体仍为三个阶段，3A 至 3E 只是第三阶段内部步骤。

本版替代 v3.4 作为后续实施依据，保留已有实现与历史报告。调整重点是：**自由布局与统一外观结合；能力随完整任务验证逐项开放；先解决自然表达下的生成稳定性，再扩大复杂交互。**

| 这次具体改变 | 实施决定 |
| --- | --- |
| 两种工具需要一致的形式选择 | 共用公共策略并保证实际请求中只装配一次；复用 SDK 已有去重，增加实际请求检查 |
| “有渲染器”容易被当成“任务已支持” | 建立任务能力清单；只有编译、事件、恢复、说明及验证齐备的能力才进入模型声明 |
| 按模块开发难判断用户收益 | 每批交付贯穿生成、操作、保存、刷新和追问的任务；复杂任务附独立结果核对 |
| 外观退化发现过晚 | 主题、字号、窄屏和预览列入首批流程；后续新图形能力继续接受同样检查 |
| 方案与成果状态混淆 | 本文描述目标；实际完成范围由分步报告与证据记录，不把计划写成支持声明 |

### 借鉴 OpenIntelligentUI 的位置

采用自由 HTML/CSS 布局、共享设计系统、CSS 就绪后预览和受限宿主桥接的思路。保留 Piora 的 AgentSession、Beta 设置、工具权限和会话持久化。参考项目的生成脚本与库在最终 iframe 中运行；Piora 的生成计算放入独立运行时，使交互状态能够保存、回放与核对。[R1]

参考项目使用单独的 Jev 形式选择服务及进程内检查点；本方案沿用当前回答模型作语义选择，也不把参考项目的通用 agent state 当成任意生成控件的持久状态。[R2] 判断基于本地固定提交，不代表对远端最新版或运行效果的测评。本轮只改文档，没有复制第三方实现。

## 2. 怎样判断文字、澄清、组件或小程序

当前回答模型在同一轮读取用户目标、最近对话、当前分支已确认的参数与结果、实际可用的能力。公共策略指导选择，程序检查可执行边界；不增加每条消息必经的分类请求，不按“预算”“模拟”等词硬触发。

| 用户表达 | 选择及原因 |
| --- | --- |
| “六个人分 480 块，每人多少？” | 文字：直接回答 80 元，操作没有额外收益 |
| “人数还没定，我想改着看总费用。” | 组件：输入与结果联动，已有组件能够表达 |
| “排序我没看懂，能一步步点着看吗？” | 小程序：有当前步骤、过程高亮与状态推进 |
| “拖动这个三角形，看看面积怎么变。” | 小程序：需要坐标、拖动和几何计算 |
| “提成规则还没定，先帮我算本月提成。” | 澄清：缺的是业务规则，做输入框也不能代替规则 |
| “为什么刚才的结果变了？” | 读取已确认状态解释，通常不重新生成 |

### 一份公共策略，一份能力声明

- 公共 answer-output 层提供同一选择策略；组件与小程序各自补充协议、约束和可执行示例。实现核对修正了本版最初的判断：两个工具虽各自声明公共规则，但 SDK 的 buildRules 已逐条去重；真实请求断言也确认每条只出现一次，无需另建重复机制。
- 能力定义包含版本、支持的事件与视图、运行限制、说明和验证用例。状态区分 planned、implemented、verified；仅 verified 且当前环境可用的能力进入模型提示，编译与接纳使用同一版本来源。
- 验证记录绑定能力版本和相关实现摘要；相关实现变更后重新检查受影响能力。测试可在隔离配置中启用实现草稿，普通会话不因“已注册工具”自动获得未验证能力。
- 形式选择不另加用户问卷。低风险布局由模型决定；必需业务事实缺失才澄清。已有输出的解释、参数修改、程序修订分别处理，保持稳定输出身份。

### 失败定位与纠错预算

原始参数校验后再编译、试运行。失败按形式选择、契约结构、运行错误、任务结果四类记录。返回稳定错误码、字段位置和可修复原因；不猜业务公式，不静默改写用户数值。

沿用同一 PromptRun 共用的 3 次接纳尝试、1 次模型纠错和首次尝试起 60 秒窗口，换工具或模型恢复不得刷新预算。这是初始配置，需经真实模型校准。失败后保留旧结果并解释原因；首次成功率与纠错后成功率分别记录。

## 3. 架构：自由表达，宿主管理执行与状态

模型提交 MiniAppPlan：用途、假设、输入、HTML/CSS 布局及计算程序。宿主将其编译为受支持的文档和图形，试运行成功并收到当前会话的发布回执后才开放交互。已有组件继续承接适合它的任务。

```text
AgentSession -> 形式选择 -> MiniAppPlan -> 编译 / 试运行 / 发布
                                      |
                                 MiniAppHost
                           /                 \
             文档 / SVG / Canvas / 3D     Worker + QuickJS
                  可信渲染器              显式状态与计算
                           \                 /
                          版本化事件与投影帧
                                  |
                    独立状态存储 / 追问 / 登记动作
```

| 部分 | 责任与约束 |
| --- | --- |
| 模型生成内容 | 决定任务布局和计算；使用普通函数、循环、数组，不再为业务公式发明表达式语言 |
| 计算运行时 | Worker 内 QuickJS/WASM 执行 init、reduce、advance、project；输入、状态、随机种子和逻辑时钟显式保存 |
| 可信渲染器 | 文档/SVG 绑定，Canvas 绘制，受限 Three.js 场景；模型程序不直接访问 DOM、网络、文件或 Electron |
| 宿主外壳 | 主题、字号、播放、暂停、单步、复位、停止、保存、状态提示和外部动作权限 |
| 通用输出层 | 管理能力、生成、预览和保存门禁；独立适配器承接组件与小程序，不把状态机塞进 ChatWindow |

project 从同一状态计算图形、数值和说明，不推进模拟。服务器重投影能够核对保存一致性，但不能证明业务公式或物理模型正确；任务正确性另有独立核对。

自由布局有明确范围：HTML/CSS 经编译，依赖随应用固定分发；不承诺直接运行任意网页、DOM 脚本或完整 Three.js 示例。这个取舍增加渲染适配成本，换取暂停、恢复与分支独立性。

Beta 关闭时停止运行并展示历史静态快照；普通聊天继续调用通用接口。开关变化也在服务器复核，旧生成或保存请求不能在关闭后迟到提交。无需再引入一套聊天后端或另一组用户开关。

## 4. 复杂任务怎样落地，怎样保证好用

以下都是第三阶段保留的范围。按通用能力组合，不为某句话编写专用演示；每一行必须有可执行说明、任务正确性检查和真实桌面证据。

| 任务族 | 实现方法 | 完成判据 |
| --- | --- | --- |
| 算法与离散过程 | 状态保存序列、步骤、高亮；单步与播放共享转换 | 过程顺序正确，元素不丢失，终态正确，暂停后可继续 |
| 几何拖动 | 统一坐标变换、捕获与释放；事件修改点位，同帧投影 | 拖动后面积/长度与独立公式一致，缩放窗口不偏移 |
| 动态列表 | 有限重复模板、稳定 key、字段与事件绑定 | 增删和重排后操作正确项目；展开节点计入预算 |
| 模拟与小游戏 | 固定逻辑步、显式随机源、按键及碰撞状态 | 规则与终态可核对，同种子/事件可回放；持续运行后可恢复 |
| 三维操作与教学 | 对象 ID 拾取；相机、缩放、选择入检查点；几何状态驱动标签 | 选中正确对象并恢复视角；教学任务核对邻接、边长、重叠与还原 |

事件携带实例、视口及显示帧身份。连续移动可以合并，按下、松开、取消和点击保持顺序；过期事件不得误操作新对象。页面隐藏、失焦、停止和卸载都释放按键及拖动。默认暂停，同一聊天视图仅一个实例持续播放。

推进方式须显式声明为无时间推进、离散步骤或连续模拟。排序等离散过程的应用按钮、宿主单步与播放必须调用同一状态转换；连续模拟由 advance 按固定逻辑步推进。无推进语义的工具不展示播放控件。验收对照各入口的业务状态与独立预期，不能只检查 tick 增加；当前排序样本已发现宿主单步不推进算法，须修复后才能计为完整任务。

资源按程序、状态、消息、节点、绘图及三维场景分别限制。现有 8 ms/步、30 fps、32 MiB 堆等仅为初始配置，不是设备性能结论；超预算暂停并保留最近检查点，不跳过逻辑步骤伪造流畅。停止释放计算与图形资源，强制终止恢复最近确认状态。

### 外观作为能力的一部分交付

宿主统一颜色、字体、间距、输入样式、焦点与播放栏；模型负责内容层级和任务布局。精确值用输入框，离散选项用选择器，连续探索才用滑块，空间任务用拖动并提供键盘或数值替代。控件都必须影响有用结果。

样式及必要依赖闭合后展示只读预览；不执行生成程序，不创建三维 GPU 上下文。正式界面同步宿主主题与字号，Canvas/三维使用语义色与标签映射。主题切换不重置状态，减少动画偏好影响播放和过渡。

首批任务检查深浅色、用户字号、窄屏、键盘焦点、加载/失败/恢复提示；复杂能力继续覆盖色彩以外的信息表达与键盘替代。设计重订时发现的固定浅色和 16px 字号已进入后续修复；实际覆盖范围以对应成果报告为准，Canvas/三维语义色等不能由基础主题同步推定完成。

## 5. 保存、追问、修订与动作

发布记录保存不可变程序及来源；交互记录保存 inputs、state、rng、tick、程序版本、stateRevision 与投影摘要。操作结果不写回原始工具回执，也不依赖浏览器闭包或 DOM 快照恢复。

```text
暂停 / 冻结新输入 -> 排空输入及 Worker 队列 -> 一致检查点
-> IndexedDB 草稿 -> 校验分支与 expectedRevision
-> 服务端重投影 / 原子保存 -> 幂等回执 -> 追问使用确认状态
```

| 用户场景 | 必须实现的结果 |
| --- | --- |
| 断网、失败或响应丢失 | 保留草稿，同一 requestId 查询回执或重试；确认后才清除对应草稿 |
| 保存中又有新操作 | 新修改保留为下一版本；旧回执不得清除更新的草稿 |
| 多窗口、旧分支、旧草稿 | 校验版本与来源；冲突保留双方并提供选择，不静默覆盖。草稿分页可找到超过首批数量的记录 |
| fork、复制、导出与恢复 | 继承当前分支可见的确认状态，之后独立写入；导出静态参数和结果；回收站恢复关联数据 |
| 关闭再开启 Beta | 停止实例并撤销旧请求；已确认结果和未确认草稿保留，重新开启不会复活旧请求 |
| 按当前结果继续问 | 完成保存后再提交。失败可重试，或明确选择基于已保存值；不悄悄用旧状态 |

### 修改程序与调整参数分开处理

调整人数、速度或点位属于同一程序的状态变化，不重新生成。用户要增加规则或交互时才生成候选版本，保持旧程序可用；跨组件与小程序切换也不能绕过修订确认。

迁移按字段含义、单位和约束判断兼容输入，内部 state 默认重新 init。需要保留运行进度时执行受限迁移，再校验和投影。展示保留、重置和丢弃的内容，用户确认后提交；确认前重新核对来源版本，失败回到旧版本。

外部动作只通过登记的宿主入口发起，先保存结果，再经过现有工具权限。加载、计时器、程序事件和 iframe 消息都不能自行取得操作授权；继续提问也由明确用户操作触发。

完整恢复矩阵覆盖断网、多窗口、取消、重载、分支、删除恢复与 Beta 切换的组合，不能用一个计数器刷新成功代表全部恢复完成。

## 6. 实施顺序与验收安排

每步交付可操作成果、Markdown 报告和 PDF。当前基础代码与固定模型聊天流程继续复用，下一步优先完成 3B 的真实模型和视觉门槛；3C 的恢复能力与 3D 的复杂交互不能互相替代。

| 步骤 | 交付与完成条件 |
| --- | --- |
| 3A 基础契约 | 编译、隔离计算、可信渲染和资源路径；最小程序执行与旧组件兼容。已有基础报告，按受影响改动复核 |
| 3B 首批完整任务 | 验证公共策略只装配一次，建立能力声明；真实模型生成、操作、保存、刷新、追问；基本分叉/复制/静态导出/回收站；主题、字号、窄屏 |
| 3C 恢复与修订动作 | 完整恢复矩阵、草稿分页、多窗口冲突、迁移确认和登记动作；失效请求、失败迁移均不覆盖正确状态 |
| 3D 复杂交互与泛化 | 动态列表、几何拖动、模拟/持续游戏、三维拾取/相机/教学；分别完成独立正确性、外观、无障碍与性能检查 |
| 3E 综合验收 | 三阶段开发完成后，执行完整 CI、封存集及人工语义验收；输出总报告，列出剩余缺口；发布另走既定流程 |

### 先用 8 个自然表达任务检验契约

2 个文字/澄清任务、2 个组件任务、4 个小程序任务，每例 3 次。小程序从排序单步、三角形拖动、倒水状态转换和棋盘步进互动入手；每个任务都包括保存与解释追问。它们是开发样本，不把这几个例子写入触发判断，也不以此替代持续游戏和完整三维任务。

测试使用用户指定的 DeepSeek V4.1。启动前核对配置与可获取的服务返回身份；历史 deepseek/deepseek-flash 别名本身不是版本证明。不能确认时记录身份待核实，不调用 V4 Pro，也不静默换模型。

### 泛化与正确性分开核对

完整集合保持 48 个初始任务：16 小程序、12 组件、12 文字、4 澄清、4 能力缺口。按任务族划分 32 开发、16 封存，每例 3 次；首批 8 例计入开发集。调试看过的封存样本转为开发样本并补新样本。可接受的多种回答形式预先标注。

分别记录形式选择、首次成功、预算内成功、任务正确性、保存一致性、耗时与设备资源。超时、漏调用、取消和失败保留在明细与分母中；模型输出的公式不能同时充当验证自己的答案。数值质量门槛在开发集基线后、封存测试前固定，静默丢失、越权及错误覆盖属于阻断缺陷。

人工语义验收与完整 CI 按用户安排留到三阶段开发后。开发中继续针对改动快速验证和桌面自动化；固定模型夹具验证产品链路，真实模型验证生成质量，两者分开报告。禁止本地发布包构建，发布产物由 GitHub Actions 构建。

## 7. 可行性、当前差距与依据

**可行，但最不确定的部分是模型遵守契约及复杂任务正确性。** Piora 已有计算、状态和聊天接入基础，适合继续复用；OpenIntelligentUI 对自由表达和视觉体验有参考价值，不能替代 Piora 的恢复与分支设计。

| 事项 | 当前可确认的依据 | 后续工作 |
| --- | --- | --- |
| 基础与聊天接入 | 已有固定模型桌面报告；真实模型排序一次发布成功，六步结果通过独立核对，宿主推进仍有缺口 | 统一推进契约，完成固定版本的自然语言重复任务 |
| 形式选择 | 两种工具引用公共策略；SDK 已去重，实际请求断言通过 | 持续核对策略与上下文，评估自然表达的选择质量 |
| 能力开放 | catalog 目前描述类型、版本、工具和 Beta；不含逐项任务验证状态 | 建立能力清单与验证记录，让声明和接纳一致 |
| 视觉与恢复 | 主题/字号同步已进入后续实现；草稿仍读取首批 20 项 | 完整视觉验证、分页、迁移确认与组合恢复 |
| 复杂任务 | 绘图与三维基础可继续扩展 | 动态列表、拾取/相机、持续模拟、教学语义及独立核对 |

### 风险与调整原则

- 若自然表达下反复失败，先按错误类别压缩契约、消除提示重复并改进可执行示例；不先增加重试次数。
- 若渲染能力不足，补通用事件、状态或视图能力并升级版本；不按某个演示提示词写业务分支。
- 若独立运行时无法表达任务，明确缺口并保留目标；改变执行边界需要另做评估，不能临时把任意脚本放进页面。
- 若桌面主题、字号或响应退化，将其视作该能力尚未完成；不等所有图形功能结束后再统一修外观。

本版最初交付仅修订方案；后续实施发现 SDK 已去重，因此补充了上述事实更正。新增产品代码、真实模型和桌面验证分别记录在成果报告中；历史通过不扩展为当前全部实现通过。第三阶段仍在开发，未宣称综合验收或发布完成。
