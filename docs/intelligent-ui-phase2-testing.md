# Intelligent UI 第二阶段体验测试

2026-10-30 · 基于第二阶段 v2.17 开发完成状态 · 自然语言手测指南

重点看四件事：什么时候出 UI、生成是否顺畅、改完的数据是否一致、保存和取消是否正常。以下保留此前对话里的 7 组测试，提示词可直接复制。

这是体验测试方法，不是通过报告。人工语义验收和 CI 仍按约定，在三个阶段开发完成后统一进行。

## 开始前

使用本次开发工作树，分支应为 `codex/intelligent-ui`。已安装的正式版或 beta 版不一定包含这些改动。

```powershell
cd C:\Users\shengjiajun\.codex\worktrees\intelligent-ui\Piora
$env:PIORA_DESKTOP_DEV_PORT = "30145"
npm run dev:desktop
```

已有本工作树的 Piora Dev 在运行时直接使用，不要重复启动。30145 被其他任务占用时换一个空闲端口。首次使用需先按锁文件安装依赖；建议 Node.js 22.19.0。不要运行 `next build` 或本地发布打包。

打开 Piora Dev，在「设置 → 实验功能 → Intelligent UI」开启功能，选择 **DeepSeek V4.1 Flash**（`deepseek/deepseek-flash`），不要选 Pro。开发版配置独立，首次启动可能需要配置模型；若实际运行切到其他模型，单独记录，不算本次指定模型结果。

新建测试对话，选择一个专门用于手测的项目目录。下面要创建 `ticket-test.md` 和 `ticket-test-2.md`，开始前确认这两个名字尚未使用。不要拿正在工作的对话或已有文件做测试。

## 1. 看它会不会乱生成 UI

两句话分别在新对话发送，避免上下文互相影响。

> 480块钱，6个人平摊，每人多少？

预期：直接回答 **80 元**，不必生成交互界面。

> 我想按绩效和工龄给大家分奖金，但具体怎么算还没定，帮我弄个分配工具。

预期：先问奖金分配的关键规则，不应直接编一套公式。句子里有“工具”也不代表必须立即生成 UI。

## 2. 测自然语言生成、修改和追问

新建一个门票测试对话，后面的第 4 至 7 项继续使用它。

> 我想做个门票费用小工具，先按4个人、每人30块。人数和票价我想自己改，看看总共多少钱。

预期：生成可操作界面，初始总额 **120 元**。不用指定工具名、组件或滑块；数字输入框也可以，重点是能修改并正确计算。

| 怎么操作 | 应该看到什么 |
| --- | --- |
| 把人数改成 6，票价改成 35 元。 | 总额变成 **210 元**；跟随参数变化的说明也应一致，不能仍写 120 元。 |
| 等界面显示已保存，再刷新，返回同一对话和分支。 | 仍为 **6 人、35 元、210 元**。不要把“正在保存”当成保存完成。 |
| 发送下面的追问。 | 直接按当前参数回答 **6 人、210 元**，无需重新生成界面。 |

> 按我刚才改的，现在几个人，总共多少钱？直接告诉我。

如果只出了文字、生成失败或重复尝试，先记录原话和实际回复。之后可以再试，但把首次结果和复测结果分开；补上工具名后成功，不算原始自然语言输入首次成功。

## 3. 测第二阶段的方案比较

另开一个对话发送：

> 周末出门有两个方案：A门票每人30块，车费一共120；B门票每人45块，车费一共60。先按4个人，把两套方案放一起，我想改人数看看哪个划算。

预期：两套方案可以一起比较，修改人数时结果联动。卡片、分组或表格都可以，不要求长得完全一样。

| 人数 | 方案 A：人数 × 30 + 120 | 方案 B：人数 × 45 + 60 |
| --- | --- | --- |
| 4 人 | **240 元** | **240 元**，一样贵 |
| 6 人 | **300 元** | **330 元**，A 便宜 30 元 |

注意：车费是每个方案的固定总额，不应再乘人数。判断“哪个划算”的说明也应跟着结果变化。

## 4. 测字段变化时是否保护旧参数

回到第 2 项门票对话，确认已保存的是 6 人、每人 35 元，发送：

> 票价改成按分填写，其他都保留。

预期：出现新旧字段核对。不能直接把原来的 **35 元**解释成 **35 分**，也不能未经确认就替换已保存参数。

先在确认前刷新一次：应能继续核对，旧版本仍受保护。再在核对界面填入 **4500 分**并确认。按每人 45 元计算，6 人总额应为 **270 元**；如果总额也用分显示，应为 **27000 分**，单位必须清楚。后续测试沿用这组参数。

如果确认前输入的值尚未保存，重开核对后再检查并填写。分别记录“旧参数是否还在”和“待确认输入是否恢复”，不要把两个状态混为一谈。

## 5. 测保存按钮

在同一个门票对话继续发送：

> 加个保存按钮，把当前结果存成项目里的 ticket-test.md。

界面生成后先确认文件尚未创建，再点击保存按钮，按当前对话权限完成操作。核对实际文件：应包含 **6 人、票价 4500 分（45 元）、总额 270 元**等当前信息，不能回到生成时的旧数值。

当前 Markdown 文件是可读文字快照，不要求一定是 Markdown 表格。点击时使用当前已确认并保存的参数；按钮旁的固定说明和实际文件是核对依据。

| 接着怎么测 | 预期结果 |
| --- | --- |
| 再点击同一个保存按钮。 | 提示文件已存在，不能覆盖；核对原文件内容没有改变。 |
| 发送下方改名提示，等待界面更新；若出现核对，先完成确认。 | 目标变成新的文件名，原文件保持原样。 |
| 把对话权限切到严格询问（ask），点击新目标的保存按钮后选择取消。 | 新文件没有创建。取消授权不等于保存成功。 |
| 再点击，选择“允许这一次”。 | 才创建新文件，内容仍是当前参数。 |

> 保存文件改叫 ticket-test-2.md。

full 模式可能直接保存；review 可能自动审核通过或转人工。没有弹出人工确认不一定是故障，应结合实际权限模式判断。

## 6. 测生成中取消

继续在门票对话发送：

> 再加张对照表，我想看看1到20个人，票价30、40、50块时分别多少钱。

生成期间点击停止。如果在新版发布前停止，旧界面和已保存参数应保留，刷新仍应保留此前的 **6 人、4500 分、总额 270 元**。这次请求本身不应创建文件。

若看到生成预览，它应是只读内容，不能提前保存或执行动作。预览是否提前出现取决于模型参数流；没看到预览，不直接判失败。

如果生成太快，停止时新版已发布，就记为“未覆盖发布前取消”，不要算取消保护通过。记录停止时是“准备预览”“已有预览”还是“新版已发布”。

## 7. 测实验开关

确认参数已保存后，关闭 Intelligent UI：交互控件应变成文字快照。重新开启：应恢复控件和已保存参数。关闭期间再发一句普通问题，聊天仍应正常工作。

如果在模型运行中切换开关，当前轮沿用开始时的模型能力，下一轮再采用新设置；前端关闭后的文字快照应立即生效。第一次测试建议等模型结束再切换，便于观察。

## 怎么记结果，怎么反馈

每项分别写“通过 / 失败 / 未覆盖”。涉及生成时，另外标记首次成功、自动重试后成功或人工追问后成功。保留每次结果，不要只记录最后成功的一次。

| 项目 | 记录重点 | 结果（手填） |
| --- | --- | --- |
| 1 触发选择 | 直接回答是否正确；澄清是否问到关键规则 | 待测 |
| 2 生成与恢复 | 首次或重试；210 元；刷新和追问一致 | 待测 |
| 3 方案比较 | 4 人同价；6 人 A 便宜 30 元 | 待测 |
| 4 单位变更 | 旧参数保护；核对后 270 元 | 待测 |
| 5 文件保存 | 点击才保存；当前值；不覆盖；取消与允许 | 待测 |
| 6 生成取消 | 停止时点；旧参数；刷新结果 | 待测 |
| 7 实验开关 | 文字快照；控件恢复；普通聊天 | 待测 |

反馈时给我：**原话、改过的参数、实际结果或报错**，再附模型名称、权限模式、截图及大致等待时间。能提供分支、提交号和是否有未提交改动更好。仅分享相关日志，不包含密钥或私人文件。

本轮整理文档，没有重新执行上述体验测试。模型仍可能选错回答形式、写错静态说明或需要纠错；这些都应保留为问题，不因为界面能显示就算通过。第三阶段的小程序、小游戏和复杂模拟不在这份测试范围内。
