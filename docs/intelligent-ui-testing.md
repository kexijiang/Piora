# Intelligent UI 第一阶段手测指南

适用日期：2026-10-28。当前功能分支已同步 `upstream/main` 基线 `d4dd66cd`（`0.5.5-beta.48`），Intelligent UI 尚未发布。已安装的 Piora 即使显示同一版本号，也不代表包含 Intelligent UI；请从下面的开发地址测试。

本指南记录操作方法和预期结果，不表示真实模型验收已经通过。阶段范围见 [功能说明](intelligent-ui.md) 和 [阶段成果报告](intelligent-ui-phases.md)。

## 1. 第一阶段可以体验什么

- 在回答中生成数字输入、滑块、下拉选择、复选框、指标、表格和条形图，也可以展示说明文字。
- 调整参数后在本地立即计算；每次拖动、勾选或输入都不需要重新请求模型。参数保存到 Piora 服务端仍会产生保存请求。
- 保存后刷新页面、继续追问；模型可以读取当前分支已保存的参数。
- 默认关闭，可在实验功能中开启。关闭后保留文字快照，重开可继续使用已保存参数。
- 兼容原有聊天发送、运行中引导与排队、取消、历史分支、分叉和复制。

此阶段没有任意 HTML/JavaScript 小程序、游戏或复杂模拟，也没有模型生成的“下单”“写文件”“请求网站”等操作按钮。实际业务操作仍通过普通对话和原有工具权限执行。界面在一份完整规格校验通过后出现，尚不支持边生成半截工具参数、边显示局部控件。

## 2. 从专用工作树启动

本次使用当前会话绑定的 `intelligent-ui` 专用工作树，分支为 `codex/intelligent-ui`。不要从共享的 `main` 检出启动这次功能测试，也不要在同一工作树重复启动开发服务。

从当前会话的专用工作树打开 PowerShell 终端，确认目录、分支与环境：

```powershell
git rev-parse --show-toplevel
git branch --show-current
node --version
Get-NetTCPConnection -State Listen -LocalPort 30145 -ErrorAction SilentlyContinue
```

建议使用与 CI 一致的 Node.js `22.19.0`。最后一条命令无监听结果时，可以使用示例端口 `30145`；若已有监听，先确认是不是本工作树已经启动的服务。其他服务占用时另选空闲端口，并同步替换下面的命令和浏览器地址，不要停止别的任务的服务。

如果尚未安装依赖，先在这个工作树执行 `npm ci --no-audit --no-fund`；已有按当前锁文件安装的依赖时不必重复安装。随后执行：

```powershell
node scripts/prepare-development.mjs
if ($LASTEXITCODE -ne 0) { throw '开发准备失败，请先解决上面的错误。' }
node node_modules/next/dist/bin/next dev -H 127.0.0.1 -p 30145 --turbopack
```

`prepare-development.mjs` 准备品牌资源和 Harmony 开发 worker。仓库的 `npm run dev` 固定使用 `30141`；这里先执行同一准备步骤，再明确使用 `30145`，避免与其他开发服务冲突。等待终端显示就绪，在浏览器打开 [本次测试页面](http://127.0.0.1:30145)。不要运行 `next build`、`npm run build` 或本地发布打包命令。

开发服务默认使用现有 Pi 数据目录；请新建一个“Intelligent UI 手测”对话，不要拿正在工作的对话测试分支和取消。选择已配置且支持工具调用的模型；如需工具确认，按当前对话原有权限流程处理。测试结束后，在启动服务的终端按 `Ctrl+C` 停止本次服务。

## 3. 开启功能并生成固定示例

1. 打开设置 → **实验功能（Beta Features）** → 开启 **Intelligent UI**。
2. 确认出现偏好已保存提示。初次使用默认关闭；如果之前已开启，显示已有选择属于正常行为。
3. 回到新的测试对话，发送下面的完整提示词。开启后从新一轮消息开始测试，不要求正在生成的那一轮立即增加新能力。

```text
请调用 piora_render_ui，在当前回答中生成一个可操作的“聚餐采购清单”，不要只给 Markdown 表格。

请使用以下控件和默认值：
- 人数：滑块，默认 4，最少 1，最多 20，步长 1。
- 每人份数：数字输入，默认 2，最少 1，最多 5，步长 1。
- 每份单价（元）：数字输入，默认 12，最少 1，最多 100，步长 1。
- 全部素食：复选框，默认不勾选。
- 取餐方式：下拉选择“自取”或“配送”，默认“自取”。本次测试两种方式都不收取额外费用。

请展示总份数、总价（元）和一张采购汇总表。总份数 = 人数 × 每人份数，总价 = 总份数 × 每份单价。
汇总表中的餐食名称随“全部素食”勾选状态显示“素食套餐”或“普通套餐”，取餐方式显示当前所选值；这两项不改变单价和总价。
所有结果通过控件引用和本地计算表达式更新，不要把计算结果写成固定数字。
不要添加下单、网络请求或文件操作按钮。生成界面后用一句话说明如何调整。
```

**预期：**回答出现标有 Intelligent UI 的可操作界面，默认总份数为 **8**、总价为 **96 元**。初次生成需要模型请求，时间取决于模型和网络；界面完成并保存后可操作，不必等待最后一句说明全部输出完。只出现文字时，先检查开关和测试地址，再请模型明确使用 `piora_render_ui`；仍失败则记录模型回复或工具错误，不计为通过。

## 4. 核心闭环：修改、保存、刷新、追问

按顺序操作，不需要再次粘贴原提示词。

| 操作 | 预期结果 |
| --- | --- |
| 人数从 4 调到 8，保留单价 12、每人 2 份。 | 总份数立即变为 **16**，总价变为 **192 元**；对话不因这次调整开始新一轮模型生成。 |
| 勾选“全部素食”，取餐方式选“配送”。 | 表格变为“素食套餐”和“配送”，总价仍为 **192 元**。 |
| 等待界面底部显示“已保存 · 后续追问可读取当前参数”。 | 只有出现已保存提示，才把这一组参数记为保存成功。 |
| 刷新页面，回到同一测试对话和当前分支。 | 人数 8、每人 2 份、单价 12、素食勾选和配送选择恢复，总价仍为 **192 元**。 |
| 发送：“只根据这个界面当前已保存的参数，复述人数、每人份数、单价、餐食类型、取餐方式、总份数和总价。不要修改界面。” | 模型回答对应 **8 人、2 份、12 元、素食套餐、配送、16 份、192 元**；不能回到最初的 4 人/96 元。 |

也可以把人数改为 6 后立即追问。发送会先等待参数保存，再交给模型；此时应按 **12 份、144 元**回答。若保存报错，发送应保留输入并提示，不能悄悄用旧值继续。后续测试前将人数恢复为 8，并等到已保存。

“控件立即重算”和“模型追问”是两次不同的观察：前者应本地完成，后者是主动发送的一次正常模型请求。不要把保存请求误认为模型请求。

## 5. 关闭、重开和普通对话

1. 确认参数已保存后，在设置中关闭 Intelligent UI。返回对话，交互控件应立即替换为文字快照，原对话保留。在线成功读取当前分支状态后，快照应包含最新已保存参数；读取失败或历史只读预览可退回原始生成快照，此时通过重开控件核对参数是否仍在。
2. 保持关闭，发送“用一句话解释为什么 8 × 2 × 12 等于 192”。普通对话应照常回答，新一轮不再获得 `piora_render_ui` 能力。
3. 重新开启，返回包含原界面的当前对话。应恢复此前已保存的控件值，再次调整仍能计算和保存。
4. 如果在模型运行中切换开关，当前这轮仍沿用开始时的能力；开关对模型从下一轮生效。前端关闭后的文字快照应立即生效。

若关闭前遇到保存错误，界面会提示；可以重试，或明确选择“关闭并在本机保留未保存参数”。后一种做法保留的是本机待恢复修改，不代表服务端已经保存。重开后如出现冲突，核对数值再选择“保存我的参数”或“加载已保存参数”。

## 6. 运行中引导与排队

先保留已经生成的采购界面。发送：“根据当前采购清单，分 10 段解释准备工作和核对步骤，不要修改界面，也不要调用外部工具。”在模型仍在回答时进行以下测试；如果模型很快结束，重试即可，不把未能赶上操作窗口记为失败。

| 场景 | 操作与预期 |
| --- | --- |
| 引导 | 将人数改为 6，立即在原有输入区选择“引导”，发送“后续说明请以界面当前参数为准，先复述人数和总价”。应先保存参数，再按原有引导机制交给当前任务；模型处理该条输入后应使用 **6 人、144 元**。 |
| 排队 | 再次开始一轮说明，运行中将人数改为 8，选择“排队”，发送“这轮结束后，请只核对当前人数和总价”。应先保存再排队，队列按原有规则处理，后续答复使用 **8 人、192 元**。 |

引导不保证截断已经输出的文字；排队不要求立刻出现在当前答复中。确认的是保存顺序、队列行为和模型处理补充消息时所用的参数。若保存失败，补充输入应保留并给出错误，不应形成无提示的丢失或重复发送。

## 7. 取消、分支与分叉

这些用例使用测试对话，先完成上面的核心闭环。

- **取消生成：**在一次模型说明尚未结束时点击原有停止按钮。已生成并保存的采购界面仍应可查看，刷新不应丢失已保存参数。尚未完成的界面规格不应作为可操作界面出现。
- **等待保存时取消：**若能观察到“正在保存”，此时提交追问并马上停止或切换聊天。确认原输入没有消失，且旧请求不会在保存完成后意外投递到新聊天或新一轮。此用例需要赶上保存等待窗口；未观察到该窗口就记为“未覆盖”。已经被服务端接收的排队项按原有撤回/取消流程处理，不把停止理解为自动删除所有队列历史。
- **原消息和新草稿并存：**在上述保存等待窗口内，原消息提交后继续输入一段不同的新草稿，再取消并刷新。新草稿应留在输入框，原消息及其附件应保留为可恢复的未完成发送记录；不能用新草稿覆盖原消息，也不能在刷新后偷偷补发。
- **分叉（fork）：**先将人数设为 8 并保存，再发送一条“请复述当前参数”，使采购界面处在这条用户消息之前。从这条用户消息使用原有分叉入口建立新对话。新对话保留的采购界面应继承 **8 人/192 元**；在新对话改为 **10 人/240 元**并保存，返回原对话仍应为 **8 人/192 元**。不要从最初生成界面的那条提问之前分叉，那段保留历史里尚无采购界面。
- **同一对话内的历史分支：**在已保存 8 人的节点之后继续一轮，记为分支 A。用原有历史导航实际切回包含采购界面的祖先节点，把人数改为 6 并保存，再继续提问形成分支 B。切回 A，应保留其原有 **8 人/192 元**；B 应为 **6 人/144 元**。仅打开历史只读预览不等于切换活动分支，预览显示文字快照属于正常行为。

分叉会产生独立对话；同一对话的分支切换仍在原对话内。两种操作都应等待待保存参数，不能用一处的新值覆盖另一处已经存在的历史状态。

## 8. 记录结果与反馈问题

每项分别写“通过 / 失败 / 未覆盖”，附上实际看到的结果。一次核心流程通过不等于全部阶段验收完成；这份浏览器手测也不代替 Linux、桌面发行包和发布验证。

问题反馈至少包含：

- 日期、操作系统、Node.js 版本、浏览器，以及实际测试地址。
- 工作树分支、`git rev-parse --short HEAD` 输出；说明是否还有未提交改动，避免只报 beta 版本号。
- 模型供应商和模型名称、实验开关状态、问题发生时模型是否正在运行。
- 完整测试提示词、复现步骤、修改前后参数、预期结果和实际结果。
- 界面底部是“已保存”“正在保存”、错误还是冲突；相关提示的完整文字或截图。
- 是否涉及刷新、关闭重开、引导、排队、取消、分支或分叉；原对话与新对话各自的结果。
- 首次界面出现、首次可操作、回答完成的时间或大致等待时长；是否每次都能复现。
