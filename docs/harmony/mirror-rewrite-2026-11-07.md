# 投屏重写与验收记录

目标：重写完整投屏功能；真实动态画面实际呈现至少 60 FPS，端到端延迟小于 200 ms。配置帧率、解码帧率、画布提交率和实际显示刷新率分开记录，不以其中一项替代另一项。当前状态：本机主要功能及下述软件测量门槛已通过；代码尚未提交或发布，物理显示与其他未覆盖范围见文末。

## 参考实现与证据

本机 DevEco Studio 26.0.0.461，`hosScrcpy-1.0.17-beta.jar`。使用 [REA](https://github.com/morluto/rea) 6.8.0 的 `inspect-native-exports` 读取 ARM64 ELF，完成导出表覆盖；`inspect-binary-layout` 因当前后端仅支持 Linux x64 而不可用，未声称恢复原生函数体。另用 `javap -c -p` 检查 Java 字节码。分析产物保留在本机可视化目录 `rea-deveco`，不把 DevEco 专有二进制放进仓库或发布包。

已核对：UiTest 扩展启动、HDC Unix socket 转发、gRPC `onStart` 发送 H.264 数据、独立 `onRequestIDRFrame`、默认 frameRate 120 / 码率参数 31,457,280 bit/s / repeatInterval 33 ms。导出表存在 ScreenEncoder、RequestIFrame、屏幕方向监听和编码帧计数。导出符号不证明所有手机支持相同帧率。

现有实现瓶颈：采集硬编码 30 FPS；观看队列溢出导致整条连接退出；主线程组包、解码及绘制；解码拥塞最长阻塞一秒；首帧健康状态与生命周期耦合。现有所有权恢复、设备代次、授权网关和媒体持久化是跨功能基础设施，新投屏继续遵守其契约。

## 新实现

独立采集会话 → 按订阅者隔离的有界 GOP 队列 → 二进制流 → Worker 收流/解码 → OffscreenCanvas 即时绘制。使用严格 TypeScript、WebCodecs 和原生 H.264 采集，避免把视频复制进 React 状态。观看拥塞丢弃完整依赖链并请求关键帧，不阻塞录屏。配置和方向变化使旧解码输出失效。网络合并读包时让出执行权给解码器，避免把短暂突发误判为持续拥塞；以 80 ms 积压年龄和容量双重限制恢复关键帧。

只在已授权 HDC 设备启动原生调试采集；不自动安装 HAP、打开手机应用、唤醒或解锁。首次 USB 调试授权及设备系统限制仍有效。

## 验收矩阵

- 真实动态画面：采集、解码、呈现 FPS 与帧间隔分布；持续运行和内存。
- 延迟：真实画面变化到桌面显示的同一事件；纯主机接收至绘制时间单列，不能作为端到端验收。
- 生命周期：打开、关闭、重连、拔插、换设备、浮窗/侧栏交接、最小化恢复。
- 媒体：截图保存/复制、录屏开始/停止/封装、旋转/断流收尾、草稿恢复、观看拥塞隔离。
- 交互：触控、拖动、滚轮、快捷键、缩放、置顶、方向变化及失效坐标拒绝。
- 自动化：协议分片、尺寸边界、GOP 恢复、取消、迟到响应、Worker 退出和资源释放。

开发阶段不运行 `next build`，不本地构建发布包。测试夹具与真机结果分别登记。

## 性能方法与未通过记录

`scripts/verify-harmony-mirror-performance.mjs` 在手机浏览器绘制带逐帧二进制编号的动态页面，通过真实 HDC/原生采集及同一 Worker 引擎解码。GPU 小区域异步读回统计不同画面编号，单列重复编码帧。主机每秒触发颜色变化，等待手机页面变化、采集、传输、桌面画布绘制与确认，记录这一往返上界；不是光学屏幕测量，也不把主机接收至绘制时间冒充端到端延迟。

隔离性能服务器绕过 Next 和桌面鉴权；真实应用完整链路由上述桌面场景另外验证。脚本默认实际 Electron，可选 Edge；报告必须注明运行时。可用 `--record=true` 同时录制 MP4、检查时间戳与关键帧并实际播放首帧。

```powershell
node scripts/verify-harmony-mirror-performance.mjs --hdc="实际 hdc.exe 路径" --serial=实际序列号 --phone=true --seconds=60 --runtime=electron --record=true
```

门槛同时要求：至少 30 秒与 25 次延迟事件、不同画面平均至少 60 FPS、每个约一秒绘制窗口至少 60 FPS、最大触发至绘制确认低于 200 ms，无超时、采样丢失或错误。若手机自身未产生 60 个不同画面，不能通过增加重复帧来宣称达标。

| 运行 | 不同画面 FPS | 最低单秒绘制 FPS | 最大延迟上界 | 结论 |
| --- | ---: | ---: | ---: | --- |
| performance-06，Edge，30 秒 | 60.25 | 59.07 | 122.33 ms | 未满足最低单秒 60；旧报告当时未加入该门槛，不视为最终通过 |
| performance-07，Edge，60 秒 | 58.59 | 78.17 | 123.27 ms | 不同画面帧率未达标 |
| performance-08，Edge，60 秒 | 58.34 | 26.44 | 503.95 ms | 发生队列恢复、一次延迟超时和一次采样跳过，未达标 |
| performance-09，Electron，60 秒，同时录屏 | 60.03 | 87.51 | 182.90 ms | 当前门槛通过；60 个统计样本、59 次延迟事件，P95 127.03 ms，无超时或探针丢失 |
| performance-10，Electron，180 秒，同时录屏 | 60.22 | 87.75 | 151.09 ms | 播放零丢帧/重连，179 次延迟事件无超时，但 GPU 探针漏采两次，严格判定未通过 |
| performance-11，Electron，180 秒，同时录屏 | 60.24 | 88.84 | 194.79 ms | 当前严格门槛通过，P95 123.46 ms，无延迟超时、探针漏采或错误，MP4 实际播放通过 |

前几轮探针使用同步/CPU 像素读回，对测量对象造成明显干扰，结果保留但不作为优化后的通过证据。performance-08 后已调整网络突发处理与绘制策略。performance-10 的测量探针最多暂存 8 次异步 GPU 读回，低于播放器可正常接收的短时解码突发；改为有界 16 次（每次仅 68 字节 PBO）后，performance-11 通过零探针漏采、相同 FPS / 延迟门槛。物理拔插和发布包尚不能记为通过。

扩展桌面场景保留两次新的失败：`desktop-e2e-7laXgw` 首次浮窗→侧栏交接超时，原画面正确保留；随后增加通过 UI 分别打开两种展示位置的开发分包准备步骤，`desktop-e2e-6A3bmR` 的交接和录像通过，但真实手机测试页未收到点击。直接 HDC 点击同一手机物理中心可生效，正在记录投屏输入请求、指针事件及手机事件定位，不能把 HTTP 200 当作输入成功。最新整体验收仍未完成。

2026-11-08，机主完成认证后确认 `screenLocked=false`，重新设置两小时熄屏覆盖，继续真机测试。performance-09 同步录制的 MP4 共 9444 包、1216 × 2688、99.408 秒（包含性能窗口前的初始化与预热），关键帧开头、时间戳单调，实际 Electron 播放通过。60 秒性能窗口和完整录像时长分开记录，继续进行更长时间复测。本次测试结束后执行 `power-shell timeout -r` 恢复原设置；测试用常亮操作没有加入生产投屏路径。

## 11 月 8 日输入与完整链路补测

- 真机点击失败原因之一：输入请求原先 15 秒超时，短于首次驱动初始化（独立实测 15.69 秒）。改为从队列开始执行时计时的 60 秒总预算，涵盖驱动 45 秒上限及租约/几何查询。16 秒慢输入浏览器回归通过，`browser-input-deadline.log`。
- 真机文本框和它的 21 个祖先容器都报告 `focused=true`。改为在手机上筛选唯一聚焦可编辑类型，保留歧义拒绝与输入后读回校验；不再并发读取每个祖先的属性。[UiTest 官方接口说明](https://developer.huawei.com/consumer/en/doc/harmonyos-references/js-apis-uitest/)也明确其接口不支持并发调用。5 项定向测试通过，`hypium-input-tests.log`。
- `warm-input-1794092163528` 已在真实应用观察到中文输入、返回、滚轮与拖动，但 30 秒绘制统计有一个 41.95 FPS 窗口，平均 95.17 FPS。该轮严格判定未通过，未删去低帧样本；收到/解码/绘制帧数相同，期间播放器丢帧计数未增加。
- 设备列表每 30 秒并发读取九项元数据，会与原生视频共享 HDC 通道。新增投屏期间延后完整元数据刷新的处理；连接枚举、离线检测和断连后的身份失效继续生效，结束采集后刷新过期信息。该处理对低帧问题的改善需完整链路复测证明。
- `desktop-e2e-eJRwzs` 在开发服务器 60 秒启动阶段失败，无投屏或交互通过结论，清理正常。此前 `desktop-e2e-JdJCz6` 保留输入超时的失败记录；后续修复使用该进程进行热更新诊断，不将调试运行改写为整体通过。
- 最新输入改动：类型检查和定向 ESLint 退出 0；协议、Worker、路由与 Hypium 定向测试 19 项通过，分别见 `typecheck-input-final.log`、`lint-input-final.log`、`core-input-final-tests.log`。元数据延后处理在这批检查之后，需另行验证。

这些结果不是所有设备、任意负载下的恒定帧率保证。不同画面 FPS 来自手机逐帧标记的平均值；单秒绘制率可包含编码器重复帧。延迟为主机触发 → 手机页面变化 → 原生采集/传输 → 桌面画布绘制确认的上界，未做光学显示扫描测量。完整应用的 30 秒统计与绕过 Next 的独立 180 秒性能测试分开保留。
