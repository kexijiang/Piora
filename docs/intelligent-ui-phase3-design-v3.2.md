# Intelligent UI 第三阶段方案 v3.2

2026-10-31 | 结合 OpenIntelligentUI 的重新设计 | 方案，不是完成报告

## 1. 目标与技术取舍

第三阶段让 Piora 根据任务生成可操作、可保存、能继续讨论的小程序：算法演示、几何拖动、模拟、轻量小游戏和三维教学。保留第一、二阶段的组件界面，两条路径共用 Beta 开关和通用回答输出接口。总交付仍为三个阶段，3A 至 3E 是第三阶段内部步骤。

这次重新核对了 OpenIntelligentUI 本地提交 `8391a94` 的源码，以及 Piora 当前未提交原型。v3.2 替代 v3.1 的实施依据；已有代码与历次报告保留。主要补充是创作契约、复杂事件、保存时序和开放条件，避免只写“支持复杂任务”却没有实现约定。

### 从参考项目采用什么

| 参考做法 | Piora 的采用方式 |
| --- | --- |
| 根据用户任务选择文字、组件或自定义页面 | 同一轮回答模型选择；沿用 Piora 上下文，不增加必经分类请求 |
| CSS 完成后显示渐进预览，预览与最终实例分开 | 采用这一体验；预览只呈现已校验布局，完整程序通过试运行与发布检查后才执行 |
| HTML/CSS、共享主题与图形库支持自由创作 | 保留 HTML/CSS 创作；通过可信文档和场景渲染器呈现，主题与控件基础样式由 Piora 提供 |
| iframe 中运行生成脚本，通过桥接启动追问 | 采用隔离展示与窄接口思路；计算放入独立 Worker/VM，追问先保存当前状态 |
| 独立生成输出作为对话中的回答产物 | 保留历史版本；补充持久状态、分支、草稿恢复和更新确认 |

参考项目的架构文档明确说明：控件状态不会自动同步给智能体，会话检查点使用进程内存。[R1] 本地源码还采用 CDN importmap 和单独的 Jev 展示路由。[R2]、[R3] 这些不能直接满足 Piora 的离线依赖、分支与保存要求。

### 为什么不直接搬整个运行时

直接采用 Websandbox 与常规浏览器脚本，模型更熟悉 DOM 和 Three.js 写法，也更容易复用网页示例；代价是还要解决通用脚本的状态提取、恢复、停止与宿主权限。继续扩展固定组件则易保存，但难表达空间操作和状态演化。

本方案选择中间路径：**自由布局 + 普通 JavaScript 计算 + 受控展示和事件接口**。代价是模型需要学习较小的运行契约，部分网页能力不可直接使用。用统一版本的契约、可运行示例和真实模型数据验证这一取舍；不宣称与 OpenIntelligentUI 任意浏览器脚本能力等价，也不以现有原型数量证明产品完成。

## 2. 触发与生成：减少模型的协议负担

Beta 关闭时，普通对话保留原有行为；开启后，模型在同一轮依据用户目的、已有事实、当前能力和已保存输出，选择文字、澄清、组件或小程序。复杂、长问题或某个关键词都不是触发依据。

| 自然表达 | 应有行为 |
| --- | --- |
| “六个人平分 480 块。” | 直接回答 80 元 |
| “人数没定，我想改着看看。” | 组件界面，调整参数即可满足任务 |
| “排序到底怎么一步步交换的？” | 小程序，提供单步、播放、复位和过程说明 |
| “拖一下这个三角形，看面积怎么变。” | 小程序，图形拖动、数值和文字同步变化 |
| “规则还没想好，帮我算提成。” | 先澄清影响计算的规则 |
| “为什么我刚才那个结果变了？” | 读取已确认状态解释；无新交互需求时不重建 |

### 一份能力契约，两个互补工具

保留 `piora_render_ui_plan`，增加 `piora_render_mini_app`。前者服务参数、比较、筛选；后者服务空间交互、过程演化和组件不能表达的计算。两者使用共同的形式选择原则，原有“不能执行 JavaScript”说明限定到组件路径。

建立版本化能力清单，统一维护输入、事件、绑定、帧结构、资源上限和能力标记；工具说明与校验器从同一清单导出可共享的定义，不能自动生成的语义通过契约测试核对。只公布已接通的能力。每个说明示例必须通过实际编译和运行，避免提示词承诺不存在的 API。

模型只负责用途、假设、输入含义、有限状态、布局和四个计算函数。依赖、消息桥、保存、权限、计时器、生命周期、版本身份和资源预算由宿主处理。预览期望先获得 CSS 和完整布局字段，但对象字段顺序不作为语义正确性的前提；供应商没有参数增量时等待最终对象。

```text
init(inputs, ctx)              -> 初始状态
reduce(state, event, ctx)      -> 交互后的状态
advance(state, fixedDt, ctx)   -> 下一时间步状态
project(state, inputs, ctx)    -> 图形帧 + 指标 + 当前文字结果
```

这里使用普通函数、数组和算术，不再为排序、碰撞或物理公式增加业务表达式语法。固定时间步与可恢复随机源由宿主提供；状态必须显式返回，project 不推进时间。需要共用的坐标或向量辅助函数，只以版本固定、可测试的纯函数扩展；不变成第二套大型页面框架。

### 一次生成失败怎么办

编译器先核对结构、引用、绑定和资源，再由服务器隔离试运行。返回稳定错误码、字段路径和可修复原因。沿用共同 PromptRun 的 3 次接纳尝试、1 次模型纠错、首次尝试起 60 秒窗口；切换工具不能重置。取消、状态冲突、权限拒绝、设备能力不足不进入模型纠错循环。预算是否需要调整由开发集结果决定，并记录策略版本。

## 3. 复杂任务如何落地

```text
AgentSession -> 回答形式选择 -> MiniAppPlan -> 编译 / 试运行 / 发布
                                      |
                                 MiniAppHost
                           /                 \
             文档 / SVG / Canvas / 3D     Worker + QuickJS
                  可信渲染器              显式状态与计算
                           \                 /
                          版本化事件与投影帧
                                  |
                    独立状态存储 / 追问 / 登记动作
```

文档输入经过 HTML/CSS 解析和允许列表编译，不直接插入生成 HTML。生成 JavaScript 只在 Worker 内 QuickJS/WASM 执行，不获得 DOM、网络、文件或 Electron 能力。iframe 承载固定的可信渲染器，通过专用 MessageChannel 接收有限帧数据。

### 通用能力与责任分配

| 能力 | 具体实现约定 |
| --- | --- |
| 算法与步骤教学 | state 保存当前步骤、数据与高亮索引；advance 推进一步，project 同时产生说明与图形。有限过程到终态后不再变化 |
| 几何拖动 | 宿主统一坐标转换和指针捕获；reduce 更新点坐标，project 计算面积等结果；数值输入或键盘提供等价操作 |
| 模拟和小游戏 | 固定逻辑步长，随机种子与 tick 可保存；按键状态进入 state，失焦清除按键并暂停。超预算暂停，不能静默跳步改变规则 |
| 动态列表 | 受限重复模板、稳定 key、标量字段绑定；重复后的节点仍计入总预算，不接收任意 HTML 片段 |
| 三维拾取 | 可信渲染器进行射线拾取，返回对象 ID、受限交点和显示帧身份；不把 Three.js 对象传给生成程序 |
| 相机操作 | 宿主将旋转/缩放手势转成标准事件，程序更新显式相机状态，渲染器应用投影；刷新恢复视角与选中对象 |
| 三维关系 | 展开、旋转和碰撞等关系由计算程序表达，网格与变换由可信适配器显示；不能把展示一个立方体算作展开教学完成 |

### 事件与帧必须能对应

拾取消息携带 viewportId、objectId、frameRevision、坐标和事件类型，并绑定实例 epoch。宿主只接受仍有效的显示帧事件；过期场景中的点击不能误落到新对象。第一版按当前确认帧处理，暂停或静止场景完成精确选择；丢弃过期事件必须可诊断。连续拖动可合并最新位置，按下、松开和点击等离散事件不能静默丢失。

动态列表与三维事件在注册工具前冻结必要协议，后续扩展标明兼容版本。当前原型有标量绑定、基础指针事件和三维网格；重复列表、拾取及相机交互仍是待补齐项。

QuickJS 的中断和内存限制、Worker 的终止机制支持上述执行边界。[R4]、[R5] 但 iframe 不等于独立进程，VM 配额也不是浏览器/GPU 总配额。另行限制节点、绘图指令、网格、消息队列和资源生命周期；依赖固定并随应用分发。

## 4. 保存、追问与版本更新是一条流程

发布记录不可变，保存计划、程序摘要、工具回执与来源；交互记录单独保存输入、state、rng、tick、运行时版本、文字摘要、分支锚点和 stateRevision。参数变化不改写原始工具回执。

### 从最后一次操作到追问

```text
用户点击追问
  -> 暂停时间推进，冻结新输入
  -> iframe 先发出尚未发送的指针事件，再确认冻结
  -> Worker 处理完已排队事件，取得同一检查点
  -> 待保存草稿写入本机恢复存储
  -> 服务器复核分支、发布版本和 expectedRevision
  -> 同一程序重新 project，原子保存并返回回执
  -> 后续模型读取确认的版本、参数、假设和当前结果
```

这一屏障解决“刚拖动完就提问，却保存了上一次结果”的问题。等待有超时；失败保留草稿和最近确认版本，并让用户选择重试、恢复或明确采用已保存状态。不能自动继续发送旧状态，也不能只等防抖计时器结束就标记“已保存”。

本机草稿用 IndexedDB 持久保存，按 session、publication、分支和独立 draftId 区分。每次写入有 requestId，响应丢失先查回执，再重试同一请求；仅删除已确认的那份草稿。一次保存过程中又发生操作时，新草稿依赖前一回执，确认后更新预期版本，不能越过未确认写入。

追问绑定此次确认的状态版本。恢复输入后发生的新操作不改写已经捕获的模型上下文；新候选发布时再次复核源版本，发现变化则保留旧版并提示，不能用旧参数生成的结果覆盖当前操作。

### 生命周期与恢复规则

| 场景 | 行为 |
| --- | --- |
| 初次生成、刷新、重新开启 Beta | 默认暂停；可操作静态控件，时间演化由用户点击播放 |
| 多窗口或断网 | 版本冲突保留双方内容；可恢复、另存草稿或明确采用服务器版本，不最后写入者覆盖 |
| 分支导航、fork、复制 | 只读取目标祖先可见状态；副本继承可验证的保留历史，之后独立保存 |
| 从旧草稿恢复 | 服务器核对源分支祖先关系和发布身份；不能只靠前端传来的 leafId 或提示标签 |
| 新版程序或输入含义变化 | 先保留旧版，展示差异并确认；同义同单位的兼容输入可预填，内部 state 默认重新 init |
| 显式状态迁移 | 单独受限转换，再校验和投影；失败不破坏原版本与草稿，不自动做含义或单位猜测 |
| 回收站和导出 | 发布与状态一并删除/恢复；导出参数、结果与静态快照，离线 HTML 不自动执行代码 |

服务器重新投影能验证保存格式和展示一致性，不能证明公式本身正确，也不证明全部状态来自真实点击。正确性另外用独立计算核对。

停止会终止计算、释放渲染资源并拒绝迟到消息；恢复从已确认检查点开始。关闭 Beta 立即停止现有实例并取消未提交的小程序发布/保存，下一轮撤销工具能力；已经确认的状态保留，恢复草稿不因关闭而删除。普通会话的既有运行仍遵守原有取消规则。

## 5. 外观、动作与模块边界

### 外观由谁负责

Piora 提供统一标题、内容边距、控件基础样式、字体、主题色、焦点、错误提示及播放/暂停等操作；模型负责信息层级、布局和任务内容。原有组件继续保持第一、二阶段的留白与对齐。自由布局不意味着每次生成都从零设计按钮。

生成时先呈现占位，CSS 与依赖完整的布局通过校验后显示只读预览；三维位置使用占位，不在预览中创建 GPU。正式实例有明确的候选、已发布、暂停、保存中、保存失败和停止状态。新版本失败时继续保留旧输出。

| 操作目的 | 默认交互 |
| --- | --- |
| 准确填写数值 | 数字输入，显示单位与有效范围 |
| 在有意义的连续区间试探 | 滑块，可配数值输入 |
| 比较有限选项 | 按钮、卡片或选择器 |
| 理解过程 | 播放、暂停、单步、复位 |
| 理解空间关系 | 拖动、选择、旋转及键盘替代 |

主题和字号从宿主同步，Canvas/三维使用语义调色板映射到实际颜色；不能让深色主题下的图形标签消失。动态说明、数值和图形来自同一次 project。窄屏允许重排，重要内容不能裁切；减少动画、键盘焦点和文字替代是交付条件。

### 外部动作与追问

生成代码只能提交本地事件。读取参数、另存结果等操作复用已登记动作，通过外层宿主按钮、当前聊天权限和幂等回执执行。动作前先保存并重新核对分支、目标和版本。生成程序和 iframe 消息不能代替授权。

可提供“根据当前结果继续问”宿主入口：先完成保存，再把经验证的参数和结果作为任务数据加入下一轮。首次加载、动画定时器或普通输入变化不能自动发消息。状态中的文字也不能变成系统指令或工具权限。

### 模块落点

`lib/answer-output-*` 维护 kind/version、生成、预览、渲染、保存门禁和复制导出的通用适配接口。现有组件保持 `intelligent-ui`；小程序登记为独立 `mini-app`，工具入口置于 `extensions/piora-mini-app.ts`。

`lib/mini-app/` 管协议、编译、计算、事件、发布、状态及恢复；`components/mini-app/` 提供 Preview 与 Surface；状态、迁移和动作 API 在会话作用域复核身份。ChatWindow、MessageView、useAgentSession 只调用通用接口，不增加小程序状态机分支。

关闭 Beta 时不加载 QuickJS、Three.js 或交互 Surface，历史使用文本快照。宿主保留会话、模型选择、SSE 与权限实现，不引入另一套聊天后端。

## 6. 实施顺序与开放条件

先用一条真实使用流程验证架构，再补齐复杂能力和全部生命周期；完整范围仍覆盖三维、模拟、持续交互、迁移、权限及泛化。步骤可交错，不能把基础模块通过测试当成第三阶段完成。

| 步骤 | 交付内容 | 完成证据 |
| --- | --- | --- |
| 3A 契约与基础运行 | 统一能力清单；计算与渲染隔离；动态列表和空间事件协议；依赖装载与取消边界 | 示例能编译运行；资源超限可停止；旧组件回归；真实开发应用能加载 Worker/WASM |
| 3B 第一条完整流程 | 正式 Surface、工具登记、共同尝试预算；同时完成 3C 最小保存与追问屏障 | 在聊天中生成教学小程序，操作、保存、刷新恢复、追问；记录实际模型结果 |
| 3C 完整生命周期 | 草稿、冲突、分支、fork/复制/导出、迁移确认、登记动作与权限 | 响应丢失、断网、重复操作、取消和旧分支写入均有明确结果及恢复证据 |
| 3D 复杂能力与泛化 | 重复列表、拾取、相机、模拟和持续小游戏；主题、字号、无障碍和性能 | 教学/模拟、持续交互、三维各至少一项贯穿产品流程，结果由独立依据核对 |
| 3E 综合收尾 | 三阶段回归、最终报告、此前推迟的 CI 与人工语义验收 | 分开记录开发完成、待验收、失败和验收通过；发布另走发布流程 |

### 接下来最先完成的工作

- 核对浏览器草稿、回执与服务器的分支恢复协议，补齐保存屏障的时序验证；当前存在代码不代表已经接通。
- 接入正式 Surface 和通用保存门禁，再登记工具、渲染器及共同生成预算。
- 在真实开发桌面运行“生成 → 操作 → 磁盘确认 → 刷新 → 追问”，随后扩展完整恢复和复杂任务矩阵。

每步维护 Markdown 成果报告与 PDF：记录对应版本、实际改动、执行命令、结果、失败及复测、未覆盖项。设计文档描述计划，报告只描述证据；本版不是新增能力的发布说明。

Piora HEAD 为 `b41fa2ff`，分支 `codex/intelligent-ui`，另有未提交原型。已存在编译器、QuickJS Worker、Canvas/Three.js、发布日志、独立状态服务、API 与只读预览。通用 catalog 和前端 renderer 目前仅登记已有组件；小程序工具尚未开放。

## 7. 验证与可行性判断

可行性判断是：现有会话、权限、输出适配与计算/渲染原型足以作为基础；主要工作在模型契约、恢复一致性、复杂交互和任务正确性。参考项目证明了可借鉴的产品组织方式，不能替代 Piora 的实际验证。本版不承诺工期或成功率。

真实模型测试遵守用户指定的 **DeepSeek V4.1**，运行前核对配置与实际返回标识；已有 `deepseek/deepseek-flash` 映射只有确认对应后才使用。不使用 V4 Pro，失败后不静默替换。

沿用 48 个初始任务：16 个小程序、12 个组件、12 个文字、4 个澄清、4 个能力缺口；32 个开发、16 个封存，每例 3 次。按任务族与交互组合隔离。封存样本被用于调试后移入开发集，并补新封存样本。自然表达、多轮引用和明确拒绝 UI 都要覆盖。

| 验证层 | 记录方式 |
| --- | --- |
| 形式选择 | 单列误触发、漏触发、形式不合适和漏澄清；允许多种合理形式的样本提前标注 |
| 生成可用性 | 首次可运行与预算内最终可运行分别统计；保留所有输入为分母，不删除超时、漏调用和失败样本 |
| 任务正确性 | 独立核对公式、规则、单位、边界与终态；模型自报“正确”不算依据 |
| 产品完整性 | 保存、刷新、追问、迁移、分支、权限、关闭 Beta 与恢复逐项记录 |
| 性能与体验 | 记录设备、版本、预览/可用耗时、输入响应、资源趋势、窄屏、主题和键盘操作；不混合软件渲染与原生 GPU 结果 |

### 复杂任务的独立核对

几何用独立鞋带公式核对面积；排序核对过程与元素多重集；模拟用固定种子回放和独立参考算法；小游戏核对输入、碰撞、计分、暂停和终态；立方体展开核对邻接、边长、重叠与还原。会动、能画或截图漂亮，都不足以证明完成任务。

故障覆盖残缺生成、错误绑定、死循环、超大状态、消息洪泛、关闭 Beta、迟到回复、发布中断、写入响应丢失、多窗口、旧草稿和迁移失败。桌面操作复用 `scripts/desktop-e2e/`，通过 UI 执行，接口只做准备与核对，明确模型夹具和真实模型的边界。

当前 30 fps、单步 8 ms、VM 堆 32 MiB、400 文档节点及 200 网格等是原型预算，不是目标设备性能结论；调整必须版本化并记录依据。每个聊天视图至多一个实例持续运行，卸载后释放资源，过多历史输出不同时启动。

### 方案自审与剩余风险

最需提前验证的是：契约过长导致模型反复失败、拖动与保存不同步、三维事件落到旧帧、状态迁移含义错误，以及原生设备资源差异。分别通过契约样例与真实模型、保存屏障、帧身份检查、显式确认、目标环境验证处理。

人工语义验收与完整 CI 仍按用户安排留到三个阶段开发后；此前继续必要的快速验证和开发自测。本轮完成源码核对、方案自审及 PDF 检查，未进行产品测试，也不是独立人员 Review。

## 8. 版本、依据与差异记录

### 相比 v3.1 的落实项

| 原先较概括的要求 | 本版补充的实施决定 |
| --- | --- |
| 统一契约、减少生成失败 | 共用能力清单、可执行说明样例；宿主承担生命周期代码，只公布已经接通的能力 |

| 草稿与分支保护 | 恢复在服务器校验祖先关系；保存中的新修改依赖前一回执，避免越序覆盖 |
| 自由布局与视觉质量 | 明确宿主设计系统、语义调色板、控件选择和同帧文字；避免重复生成基础控件样式 |
