## 1. 目标、证据与范围

用户已进行第一阶段实测：自然表达下可能生成失败，也可能多次重试；另外，何时选择交互界面与跨场景泛化同样重要。现有反馈没有逐次调用记录、具体模型及成功率，不能把失败根因直接归为提示词或模型能力。

第二阶段首先实现“自然表达 → 合适的回答形式 → 稳定生成 → 修改、保存、继续追问”。组件扩展、增量生成和受控动作继续保留，但排在稳定生成之后。第三阶段仍为隔离小程序、模拟和小游戏，本方案不引入任意生成代码。

第一阶段代码基线的事实依据：

- `extensions/piora-intelligent-ui.ts` 通过工具说明引导模型选择 UI；没有独立决策器。工具参数包含深度 12 的嵌套表达式 schema，示例主要为人数滑块和计算。
- `lib/intelligent-ui/protocol.ts` 的 v1 Surface 支持八类节点；表达式只允许引用控件。限制为 64 节点、4096 个表达式节点、深度 12，以及当前按 JSON 字符串长度计算的 64000 上限。
- `components/AnswerOutput.tsx` 通过通用封套加载独立渲染器；未知版本或失败有文字快照回退。当前不是半截工具参数的增量渲染。
- `lib/intelligent-ui/store.ts` 和客户端状态模块已处理分支、界面版本、参数版本、冲突与本机恢复；这些约束必须保留。

可行性判断：先保留现有渲染协议，增加模型输入规范化和通用编译层，能控制第一步的影响范围。是否能提高自然语言首次成功率仍需实测；换协议并不自动提高语义正确性。

交付原则：模型表达任务关系，宿主验证并组织界面；不把业务规则交给宿主凭空推断。触发选择、任务正确性、协议正确性和持久化成功分别记录。

## 2. 触发策略：意图、收益、能力和上下文

默认在当前模型请求内完成选择，不对每条消息额外调用一个分类模型。新增一份独立、版本化的决策策略，通过现有扩展提示注入；工具说明从列举业务场景改成说明交互收益和能力边界。

| 条件 | 推荐行为 | 宿主能保证的边界 |
| --- | --- | --- |
| 新轮次开始时功能关闭或能力不可用 | 普通文字回答 | 不提供生成能力；进行中沿用原能力快照，前端关闭则保持文字回退 |
| 用户明确要求可调整、筛选、配置等交互，任务可表达 | 创建或更新 UI | 仅接纳当前组件能力范围内的结构 |
| 用户需要反复换条件并观察联动结果 | 优先 UI | 必须存在真实输入与输出关系，不能只有装饰控件 |
| 一次性计算、问答、解释或静态比较 | 直接文字或普通表格 | 不用关键词强制触发 |
| 关键信息缺失，影响结论或规则 | 简短澄清 | 不替用户杜撰价格、计算规则或数据来源 |
| 需求明确但当前能力无法表达 | 说明边界，提供可用替代 | 不伪造按钮、数据、计算或成功状态 |

上下文规则：同一任务初次可以文字回答；用户开始调整条件时再生成界面。针对已有界面的解释不重新生成，结构变化使用同一逻辑任务的更新。明确“只要文字”的要求优先。可以默认的低风险展示选项应明确说明；缺失的业务事实不能伪装成默认值。

正反例成对编写：一次分账金额与可调整分账器；静态优缺点与动态价格比较。策略覆盖“改变条件、选择方案、配置选项、观察变化”等通用意图，不以“预算、露营、计划”等词作为路由规则，也不固定绑定特定组件。

这是一套模型选择策略，不是假装已有可靠的规则分类器。宿主只执行明确的能力开关、协议和预算约束；其余选择是否正确，通过完整对话级评估确认。若同轮决策仍不稳定，再用证据评估额外分类器的收益和延迟，默认不引入。

## 3. 生成协议：先简化输入，保留可信渲染

新增独立的模型输入契约 `UiPlanV1`，作为生成中间表示。它与持久化的 `UiSurface.version=1` 是两个版本空间，不能把前者直接塞进旧封套冒充可渲染数据。

| 模型提供 | 宿主负责 | 明确不做 |
| --- | --- | --- |
| 稳定的任务与字段 ID、标题、必要说明 | 结构与 ID 校验、能力检查 | 从标题猜身份或自动改已有 ID |
| inputs：数据类型、默认值、允许范围或选项、可选单位与展示意图 | 选择数字输入、下拉框、勾选；只有明确提供范围且适合连续调节才选滑块 | 为了能显示滑块而编造上下限 |
| derived：命名的平铺运算节点 | 检查引用、循环、类型、成本；编译为现有表达式 | 解析或执行任意 JS/字符串公式 |
| views：指标、明细表、对比图及字段引用 | 生成稳定节点、确定顺序和基础布局 | 从“帮我做预算”自行发明价格与计算公式 |
| 假设、数据来源说明和必要提示 | 展示给用户并保留在上下文 | 把模型假设标成已验证事实 |

平铺计算示例（字段契约示意，尚未实现）：

derived 和 views 只允许常量、input 引用和 derived 引用三类原子值；不接受内嵌运算或字符串公式。input/derived 共用唯一符号空间，view ID 也不得冲突。宿主不把 derived 伪装成可编辑控件。排序和类型检查不执行计算；求值从被展示结果按需向下进行，保留 `if` 未选择分支不求值的行为。

```json
{
  "inputs": [{"id":"people","valueType":"number","label":"人数","value":4,"min":1,"step":1}],
  "derived": [
    {"id":"servings","op":"multiply","args":[{"input":"people"},{"literal":2}]},
    {"id":"total","op":"multiply","args":[{"derived":"servings"},{"literal":12}]}
  ],
  "views": [{"id":"totalView","kind":"metric","label":"总费用","value":{"derived":"total"}}]
}
```

这能让模型复用命名结果，减少重复嵌套；它仍然需要正确表达“每人两份、每份十二元”的业务含义。单位先作为受校验的语义与展示元数据，不承诺自动换算或货币计算精度。

编译器按顺序完成：解析与输入上限检查 → 引用解析/环检测 → 类型及运算元数检查 → 成本预估 → 有界展开 → 现有 `validateSurface` → 默认参数求值检查 → 形成候选界面。允许前向引用，使用拓扑排序，不依赖数组先后顺序解释计算。

平铺计划不能绕过现有预算：共享子图展开前计数，在 4096 表达式节点、深度 12、64 控件与展示节点和现有序列化长度限制内才可编译；超过即报复杂度错误，不无限展开。计划本身也设数量和序列化长度上限，具体阈值在协议原型中固定。

除零、非有限数和输入边界在生成、交互两处检查。不能只用默认值通过就宣称所有输入安全；保留交互时的错误显示，不把异常结果转成 0 或静默夹紧输入。`if` 保持惰性分支语义，类型检查避免依赖不执行分支的数值求值。

## 4. 工具接入、兼容和状态提交

实验对比阶段在一次 PromptRun 开始时选择旧输入协议或新计划协议，只向模型暴露一个生成入口。建议新计划原型使用独立内部工具名，避免把两种大型 schema 合并成同一工具的递归 union；对用户统一显示 Intelligent UI。旧工具结果和旧 Surface 永久保持可读，切换实验组不改变历史记录。

生成、规范化、编译均在独立功能模块完成，聊天公共层仍仅识别 answerOutput。新增工具身份必须同时更新扩展注册、加载能力签名、运行中能力快照及测试；当前 `loadedBetaFeatureSignature` 只检查 `piora_render_ui`，不能遗漏这个调用方。

编译后的不可变 Surface 才是历史渲染依据；planVersion、compilerVersion、输入摘要及诊断存入 journal，不向严格的 v1 Surface 填入未知字段。旧历史工具参数不自动重放到新工具：普通“重试消息”按当前能力重新生成；明确的旧调用复现只在固定旧协议的测试环境运行。更新已提交 Surface 必须生成新版本，不在相同缓存身份下替换内容。

| 标识 | 责任与用途 |
| --- | --- |
| planVersion / compilerVersion | 描述生成输入与编译行为；用于复现和灰度，模型不能指定编译器版本 |
| Surface.version / surfaceRevision | 持久化协议与界面结构版本；服务端分配、核对 |
| stateRevision / branch anchor | 用户参数的并发与历史分支边界；不能用新生成绕过冲突 |
| promptRunId / toolCallId / operationId | 取消、预算、诊断和幂等关联；operationId 由宿主绑定，不信任模型自报 |

现有组件按工具调用标识挂载，并非统一“替换当前界面”的事务容器。第二阶段需显式增加候选与已提交版本的概念：验证后的候选先展示为只读预览；原有界面继续可读且参数不被覆盖。只有绑定当前会话、分支、运行身份，且源参数版本仍匹配时才发布新版本。

源参数版本在模型请求构造、UI 状态加入上下文时由宿主捕获，绑定 session/branch/surface/stateRevision 和摘要，不能等 execute 结束后才读取最新状态冒充生成依据。模型不能改写这个凭据；供应商重试沿用原凭据，新的上下文快照必须建立新的候选绑定。

提交前等待发起窗口已知 writer 的持久化，并在锁内复核分支与已确认参数版本；生成期间服务端参数发生变化时处理冲突，不静默覆盖。类型、单位或选项语义改变时不能仅凭同一 ID 继承值，要求明确迁移或用户确认。旧数据没有语义元数据时采用保守兼容规则，不推断等价。

取消、切换分支、迟到结果或失败候选不成为最新可编辑版本。成功提交采用内容摘要及服务端操作标识防重复；同一工具结果的重传不会生成新版本。生成成功与参数“已保存”分别显示，持久化确认仍以服务端回执为准。

这一提交边界属于新增工作，不能假设当前 store 已自动覆盖候选事务。采用以下持久化约定：

1. 新增独立的 generation journal，按会话和分支保存宿主生成的 operationId、运行 epoch、源版本、内容摘要，以及 candidate / committed / aborted 状态。旧 v1 参数文件继续保留；新生成的已提交参数、状态版本和活动指针在同一 journal 中原子写入，避免跨文件双写伪装成原子事务。
2. 新事务使用 v2 answerOutput 封套，内部编译后的 Surface 仍为 v1。旧读取器不把这个封套识别为可编辑 v1 输出，而显示文字快照。新读取器必须查 journal，只将 committed 且实际分支包含对应已落盘工具记录的候选计入活动界面；不能只靠前端状态。新历史不由旧编译器重新解释。
3. 提交顺序为：创建 candidate journal → 将带摘要的候选工具结果持久化到会话 → 获得准确 entryId 的磁盘回执 → 在会话变更互斥和 journal 锁内核对运行身份、分支、源参数版本及摘要 → 一次原子替换 journal 的 committed 状态、参数和活动指针。最后这次替换为发布线性化点。仅本操作自己的候选记录允许推进原叶节点；其他导航、轮次或写入按冲突处理，不能宽泛接受任意后代。
4. 崩溃前未完成 committed 写入的 candidate 不自动发布。重启后旧 epoch 失效，缺回执或过期候选标记 aborted；保留旧版本及原消息恢复副本。提交已完成但确认丢失时按 operationId 返回原提交结果。journal 和工具记录不匹配时停止编辑、保留旧快照并报告恢复错误，不猜测成功。
5. 历史读取、最新版本判断、参数写入、追问上下文、导出、fork/复制、回收站与永久删除统一通过“legacy v1 + committed v2”的读取适配层；fork 仅继承保留分支中的 committed 数据。旧客户端可以查看新输出的快照，不能承诺它能编辑新事务界面。新服务端拒绝旧客户端对已被取代版本的写入。
6. 发布前 flush 发起窗口已知的旧 writer，发布时再次 CAS 已确认 stateRevision。服务端无法看见其他窗口或离线窗口尚未提交的草稿，不能保证发现并阻止所有未保存修改；新版本可以在这些情况下发布，但旧草稿必须留在本机恢复记录。窗口刷新/重连后将其标记为 superseded 冲突，禁止自动写入新版本。用户可核对并迁移兼容值、加载最新并保留旧草稿，或明确放弃旧稿。只有已确认保存/迁移/保留为独立恢复记录的旧 writer 才从发送 flush 集合退出，不删除原稿、不无限 409 阻塞发送。发起窗口已知正在产生的新编辑优先保留并暂停自身发布；本阶段不引入全窗口冻结承诺。

legacy 参数 PUT、新 journal 参数写入、候选发布和分支变更必须采用同一会话锁域；锁顺序固定为会话变更锁、legacy 状态锁、journal 锁，并覆盖共享数据目录的进程边界。锁内读取权威分支与版本，拒绝已被取代输出的写入，不能依赖单个渲染器或进程内缓存。是否能安全接入所有现有调用方是 2B 原型退出门槛。

superseded 恢复是新增客户端状态机，不能复用当前针对旧 toolCall 的重试按钮。迁移时重新读取目标版本、让用户核对字段含义，创建绑定目标版本的新草稿，保存成功后才确认原恢复记录已转交；失败则两份记录关联保留，禁止合并到错误会话。选择“加载最新并保留旧草稿”时将旧稿从待发送集合移入可查看的独立恢复记录，明确提示后续追问使用最新已保存参数；这不等于旧稿已保存到新界面。

实施前必须在每个持久化步骤注入中断，验证刷新、取消、重连、两窗口并发、生成期间改参、fork 和祖先导航。还必须确认真实 SDK 可提供上述磁盘回执和会话互斥边界；缺少时先完成适配，不发布这个事务路径。回滚到旧代码保留原 v1 数据，新 v2 结果只保证文字快照可读，不自动迁移或删除新参数。

## 5. 错误、修复预算和可观察性

校验返回有界的结构化诊断：`code`、字段路径、期望类型或约束、是否允许模型修复。禁止将整个用户参数、文件内容或任意服务端错误直接作为日志或“纠正指令”回灌。返回给模型的数据继续作为不可信任务数据处理。

| 错误类别 | 处理 |
| --- | --- |
| 可证明不改变含义的格式差异 | 宿主规范化，例如拓扑排序；不删除必填字段或猜测引用 |
| 参数结构、引用、类型、运算元数错误 | 返回精确诊断，允许一次模型修复 |
| 任务语义或输入事实不清楚 | 澄清或保留文字答案；结构校验不能替代业务正确性 |
| 能力或复杂度超限 | 明确说明边界；只有不改变任务目标且用户可理解时提供简化替代 |
| 保存冲突、取消、过期身份 | 走原状态恢复与冲突流程，不让模型反复生成来“修复” |
| 网络、鉴权、供应商限流 | 由原模型请求策略处理，不叠加一套 UI 网络重试 |

原型采用保守的宿主预算：每个 PromptRun 最多 3 次 UI 工具尝试，总计最多 1 次模型纠错；从首次 UI 尝试开始计 60 秒活动窗口。多界面或同界面更新共用该预算，改变 surfaceId 或工具别名不会清零。以上是待验证的初始参数，不是已测得的最优值，也不意味着端到端等待最多 60 秒；首次工具调用之前仍由现有请求超时控制。

预算应由 PromptRun 级登记和接纳点执行，不能仅写在提示词里。参数解析失败可能发生在扩展 execute 之前；原型必须覆盖 SDK 参数校验失败、重复调用、嵌套工具、模型回退和重试等入口。无法计数的入口不得宣称已有预算保证，应在接入完成前阻止该生成路径上线。

当前依赖的 `@earendil-works/pi-agent-core/dist/agent-loop.js` 在 `validateToolArguments` 之后调用 `beforeToolCall`；普通工具执行开始事件位于较早阶段，但 SDK 内嵌工具执行不一定发出相同事件。预算接入需要关联原始工具事件/模型消息、截断参数失败与实际执行接纳，并验证顺序；仅订阅事件可观测，不等于已有原子阻断能力。若现有 API 无法覆盖，需补 SDK 接纳钩子或明确禁止未受控嵌套 UI 路径，不能用提示词补偿这个缺口。

计数定义：宿主在 UI 工具调用接纳前分配 attemptId；任何进入参数校验的新尝试都占用总次数。首次可修复错误之后的下一次 UI 尝试即使用唯一纠错额度，不依赖模型自报“这是重试”，也不因换 ID 或换工具别名而重置。再次可修复失败即终止该 UI 操作；已成功后的新界面或结构更新仍占总尝试次数。相同 toolCallId 且内容摘要一致的传输重放返回缓存结果，不重复编译/提交；相同 ID、不同内容作为冲突拒绝。供应商网络重试沿用原逻辑身份，新的 UI 工具调用才新增尝试；所有时间均计入原截止时间。

同一运行的模型回退与重连沿用计数及截止时间，不自动延长；显式新用户请求才建立新预算。取消立即撤销接纳资格。达到预算后停止接受 UI 尝试，允许模型给出文字结论；若继续重复调用，则通过现有任务终止机制停止循环，由宿主显示可理解的失败状态与已有快照，不再自动发起补救模型请求。

诊断与评估默认仅保留本地的版本、匿名任务类别、错误码、次数、阶段耗时和终态，不采集完整原文、参数值或思考过程，不发送外部遥测。原始失败材料由用户明确提供并做脱敏；基线样例使用合成数据。

## 6. 泛化评估与完成门槛

不能只统计 UI 工具调用：未调用时无法从扩展日志知道漏触发。离线评估以完整用户任务及全部最终回答为样本，人工标注“应交互 / 应直接回答 / 应澄清 / 两者均可”，结合实际工具调用和最终产物判分。模型解释或自报分数不作为真实标签，不读取隐含推理。

首轮合成集建议 60 个基础任务：30 个能力范围内应交互、20 个应直接回答、5 个需澄清、5 个能力不支持的任务；另外用独立故障场景覆盖功能关闭和用户取消。覆盖计算、比较、条件清单、配置、数据展示等领域；一部分包含普通语言的多轮更正。按业务领域、交互组合和同义改写的族整体分割，40 个开发任务、20 个封存验收任务，不把同一模板的改写分到两边。该规模用于原型比较，不代表生产统计保证。

能力内集合在运行前依据固定的组件/模型能力表标注，失败后不得把样例改标为“不支持”。关闭、不支持、用户主动取消分别报告计数及处理是否正确，不混入能力内成功率；模型自行停止、超时、供应商错误保留在端到端失败中并分层报告。取消故障用例仍须验证取消后不发布。所有排除原因公开统计。

基线与候选使用相同模型版本、设置、任务上下文及次数；至少选两种实际可用模型，每任务独立运行三次。先冻结标签、分组、预算和判分规则，再进行对比。验收集一旦用于修复，就降级为开发集并补充新的封存任务；暂缺模型或预算时如实标记不具备跨模型结论。

| 指标 | 分母与成功条件 |
| --- | --- |
| 选择漏触发率 | 能力内应交互任务中，没有选择任何 UI 工具尝试的比例 |
| 生成/提交失败率 | 已选择 UI 的能力内任务中，未形成正确已提交界面的比例；同时报告其占全部应交互任务的比例 |
| 误触发率 | 应直接回答任务中生成不必要 UI 的比例 |
| 首次可用率 | 应交互任务中，首次尝试即满足语义、计算、联动和恢复要求的比例；未调用也计失败 |
| 最终可用率 | 应交互任务中，预算内完成同等要求的比例；文字降级不能记为 UI 成功 |
| 修复率与耗时 | 按全部应交互任务报告次数和端到端时间，同时展示成功子集；失败、超时不从分母删除 |
| 澄清质量与恢复 | 缺信息任务是否问关键问题；已生成 UI 修改后是否正确保存、刷新、追问 |

标签“两者均可”的任务单列，不用于夸大漏触发或误触发指标。技术检查用独立期望值和交互步骤；语义及触发选择至少两人独立判断，分歧复核。报告按模型、任务类别和封存集拆分，给出实际计数、失败案例及区间，不能只汇总平均值。

泛化统计单位为独立基础任务/任务族，三次重复是稳定性观察，不能当成三倍独立任务。分别报告任务数和运行数，区间按任务族聚类计算；样本不足时仅报告原始计数并说明不能得出稳定结论。正式验收前固定关键类别最低独立任务数，20 个封存任务不自动满足所有类别门槛；不足则先扩集再验收，禁止用总均值掩盖类别失败。

当前没有真实成功率基线，因此不虚构绝对数值承诺。2A 测量完成、候选调整前固定可接受的首次/最终成功率、误触发率、修复及延迟预算；没有明确记录目标与封存结果，就不能把 2B 标为已验收。必须守住的硬门槛是：能力和权限不可绕过、预算不可绕过、错误更新不破坏旧参数、普通文字路径不因开关异常不可用。

只读协议实验确认：重复引用的平铺 DAG 不能保证小型 v1 输出。示例 10 个派生节点展开后有 2047 个 AST 节点；11 个时序列化约 69786 字符，超过现有限制。另一个例子 `add("oops",2)` 可通过结构校验但不能计算；`if(x==0,0,1/x)` 在 x 为 0 时可正常求值。因此方案明确有界展开、单独类型检查和惰性求值，不将结构通过当作任务正确。
