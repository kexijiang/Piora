## 1 触发判断怎样实现

当前方案是同一轮模型判断加程序约束。每次请求使用版本化策略 `intent-1`；正常聊天层无需判断“预算”“计划”等词，也没有额外的分类模型请求。开启 Beta 功能时才向模型提供对应能力。

| 判断依据 | 预期行为 |
| --- | --- |
| 一次性计算、解释、写作、静态比较 | 用文字或普通表格回答 |
| 用户需要反复改条件并观察有意义的联动 | 能力范围内创建或更新 UI |
| 缺少会改变结论的价格、规则、数据来源 | 先澄清关键事实，避免编造 |
| 只缺颜色、布局等低风险展示细节 | 系统选择合理默认值 |
| 已有 UI，用户问结果原因 | 结合已保存参数解释，不重新生成 |
| 已有任务需要增加比较项或修改结构 | 使用稳定任务 ID 更新 |
| 明确要求纯文字，或当前能力无法表达 | 尊重形式要求；说明能力边界并给可用替代 |

“480 元六个人分”直接回答每人 80 元；“人数和费用我想自己改着看”适合 UI。前一轮回答金额、后一轮要求可调整，是文字转 UI；已有 UI 后问“为什么”，则转回文字解释。相同话题可以采用不同回答形式。

模型同时读取当前分支的已确认参数、任务 ID、界面版本、参数版本和摘要。上下文保留完整 JSON，超过长度时明确标记省略，优先保留近期任务；未保存参数不会伪装成已保存值。这些内容是任务数据，不能作为工具授权或覆盖系统规则。

程序保证功能开关、协议和成本限制，不能保证语义选择正确。是否选对形式、计算是否符合任务、结构是否有效、是否真正保存分别评估。若同轮决策在完整评估中仍不稳定，再比较额外分类器的收益和延迟，当前不预先增加这笔成本。

## 2 本轮成果与接入边界

| 工作项 | 当前成果 | 仍需完成 |
| --- | --- | --- |
| 2A 策略与评估 | 版本化决策策略已接入；60 个合成任务按开发与封存集合划分；记录未调用 UI 的回答及逐轮选择 | 完整基线、独立语义验收、锁定目标、封存集复测 |
| 2B 计划编译 | 平铺输入与命名计算原型；检查引用、环、类型、运算参数数量及展开成本；编译回可信 Surface v1 | 接入真实工具和持久提交后再决定是否替换原协议 |
| 2B 运行预算 | 已接入 SDK 参数校验前接纳、普通及嵌套调用、截断调用和 PromptRun 绑定；真实 wrapper 回归通过 | 与新计划、候选提交和 UI 错误状态继续集成 |
| 2B 候选提交 | 独立 journal 原型、准确磁盘回执、版本比较、幂等和故障注入测试；支持观察同轮多个 SDK 工具结果 | 正式运行时连接、统一锁域、历史读取与客户端恢复 |
| 2C 丰富交互 | 设计保留分组布局、方案卡片、筛选表格、可取消的已校验预览 | 尚未实现 |
| 2D 动作和交付 | 保留受控动作、权限、幂等及端到端交付要求 | 尚未实现或验收 |

预算原型为每个 PromptRun 最多 3 次 UI 尝试、最多 1 次模型纠错、首次 UI 尝试后 60 秒活动窗口。它不是每个控件的额度，也不代表整个对话最多等待 60 秒。网络重试和模型回退不重置逻辑身份。参数校验前失败也要计数，不能只在工具 execute 中拦截。

计划编译器没有任意 JavaScript、HTML 或字符串公式执行能力。默认数字输入框；只有明确、合理的边界和连续调整需求才使用滑块。它简化模型表达方式，但不会自动推断业务公式，也不会保证生成质量提高。

候选 journal 原型尚不能视为生产事务：SDK 会自行写入工具结果，适配必须观察准确的磁盘回执，不能重复追加；旧参数写入、分支导航、候选发布还要统一并发边界。新版本发布与未保存草稿恢复仍属于 2B 的交付范围。

## 3 真实模型试跑结果

本次试跑使用 6 个开发任务族、2 个模型、3 种协议或策略、每组 1 次，共 36 个完整任务记录。任务包括 3 个应交互、1 个直接回答、1 个先澄清和 1 个能力不支持的场景。模型为 DeepSeek Flash 和 DeepSeek V4 Pro；未读取封存集模型输出。

固定条件：low reasoning，最多 4096 输出 token，每轮最多 4 次模型请求、8 次工具尝试，供应商重试为 0，适配器超时 90 秒。该实验预算与生产候选预算不同；只比较同一实验环境，不据此宣称生产上限已验证。

| 模型 | 策略 | UI 首次结构有效 | UI 最终结构有效 | 3 个 UI 任务的调用总数 |
| --- | --- | --- | --- | --- |
| Flash | 第一阶段 | 2/3 | 3/3 | 5 |
| Flash | intent-1 | 3/3 | 3/3 | 3 |
| Flash | plan-1 | 1/3 | 3/3 | 5 |
| V4 Pro | 第一阶段 | 2/3 | 3/3 | 4 |
| V4 Pro | intent-1 | 2/3 | 3/3 | 4 |
| V4 Pro | plan-1 | 1/3 | 3/3 | 5 |

36 次试跑中，34 次完成适配器对话流程，2 次记录为 timeout。timeout 分类还包含输出截断或请求次数耗尽，不能都理解为等待超过 90 秒。完成对话不等于交互产品可用。

直接回答和先澄清的样例，在六个模型/策略组合中均未调用 UI。能力不支持样例仍出现不合适的尝试：Flash 第一阶段调用 2 次，Flash intent-1 调用 1 次且输出截断。其余组合没有 UI 调用，但其中 V4 Pro 第一阶段未完成对话，不能计为正确解释能力边界。

旧协议曾因生成引用或表达式不符合规范而多次重试；平铺计划也出现 PLAN_ARITY 与 PLAN_SHAPE。当前小样本没有证明新协议提高首次成功率。普通语言策略在 Flash 的三个 UI 样例上表现较好，样本不足以证明跨领域或跨模型改善。

结构检查还不能替代语义验收。抽查中，某个旧协议输出声称金额保留两位小数，却使用整数 round 运算；默认人数下结果仍恰好正确。这说明需要同时核对变更输入后的计算和对结果的文字解释。

试跑只运行隔离模型与编译器，不接浏览器、保存、刷新或真实任务权限。没有把 committed 标为 true，也没有伪造独立人工评审。此处的“结构有效”不能称为首次可用率、最终可用率或生产验收结果。明细和冻结实验摘要见 [试跑证据](verification/intelligent-ui-phase2-pilot-2026-10-29.json)。
