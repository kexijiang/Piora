# Intelligent UI 第三阶段方案 v3.6

2026-10-31 | 结合 OpenIntelligentUI 与首批 24 次真实模型记录重订

## 1. 目标与这次调整

让 Piora 把有操作价值的回答变成可探索、可保存、可继续讨论的小工具。用户自然描述目标；模型选择文字、澄清、组件或小程序。整体仍为三个阶段，3A 至 3E 是第三阶段内部交付顺序。

**保留自由布局、独立计算和持久状态，先解决协议易用性与完整任务，再扩大复杂交互。** 本版替代 v3.5 作为后续依据；已有代码与报告继续保留，不把下述设计写成已完成功能。

| 首批实测暴露的问题 | 对方案的具体调整 |
| --- | --- |
| 18 次 UI 请求仅 7 次首试成功，14 次最终发布 | 优先统一工具契约、完整示例和纠错反馈；暂不增加重试次数 |
| 小程序与组件的 planVersion 混淆，纠错漏 purpose | 示例必须包含全部必填字段，分别随工具生成和验证；纠错明确当前工具、版本和完整对象要求 |
| 顶层变量、CSS 与字符串边界反复出错 | 减少非必要限制；用实际编译器生成能力说明，支持范围与示例同步演进 |
| 已发布计算器在 0 杯时除零 | 发布检查加入输入边界采样；任务验证使用独立预期，不能只看初始画面 |
| 渲染基础容易被误当成任务已完成 | 能力声明绑定实现版本和证据；生成、操作、恢复、结果正确分别记录 |

首批 8 个开发任务各运行 3 次，共 24 次。6 次文字/澄清请求均未调用 UI；18 次 UI 请求的首次发布率为 7/18，预算内发布率为 14/18。它们是小样本生成基线，不是产品成功率；本批尚未完成全部样本的浏览器操作、保存、刷新、追问或人工语义验收。

## 2. 借鉴哪些，保留哪些

参考本地 OpenIntelligentUI 的固定提交 8391a94c：自由 HTML/CSS、共享设计系统、CSS 完整后再预览、经宿主校验的桥接，均适合 Piora。它的最终 iframe 运行生成脚本；任意控件状态并不会自动同步回 agent，进程内会话检查点也不能代替 Piora 的持久交互状态。[R1]

Piora 保留现有 AgentSession、Beta 设置和工具权限，采用同一回答模型作形式选择；参考项目的独立 Jev 路由服务不作为新增必需依赖。保持小程序计算、渲染和存储独立于普通聊天模式。当前只是参考设计，没有复制项目代码；引用依据是本地源码，未声称测评其远端最新版或运行质量。

## 3. 架构与形式选择

```text
AgentSession -> 形式选择 -> MiniAppPlan -> 编译 / 试运行 / 发布
                                      |
                                 MiniAppHost
                           /                 \
             文档 / SVG / Canvas / 3D     Worker + QuickJS
                  可信渲染器              显式状态与计算
                           \                 /
                          版本化事件与投影帧
                                  |
                    独立状态存储 / 追问 / 登记动作
```

Beta 关闭时采用原有对话体验；历史 UI 展示已确认的静态结果。开启后在通用 answer-output 层加载独立适配器。ChatWindow 只接收通用输出与保存结果，不承载小程序状态机。关闭 Beta 时服务端也撤销旧生成和保存请求，重新开启不能复活旧请求。

### 由上下文决定交互是否有用

同一回答轮读取用户目标、对话事实、当前分支已确认的参数和结果，以及实际可用能力。公共策略只装配一次；SDK 已具备规则去重，本轮不重复建设。

| 判断依据 | 回答形式 |
| --- | --- |
| 一次性事实、计算或解释，操作没有额外收益 | 直接回答。例如六个人分 480 元，回答每人 80 元 |
| 缺少必要业务规则或事实，不能可靠计算 | 简短澄清；不能用一个表单掩盖缺失规则 |
| 改参数、比较结果，已有组件能够表达 | 组件 UI；按输入含义选数字框、选择器、复选框或滑块 |
| 需要过程推进、空间操作或自定义计算 | 小程序；以可执行能力为边界选择文档、SVG、Canvas 或 3D |
| 解释刚才结果、调整现有参数 | 复用已确认输出；只有规则或交互变化才修订程序 |

上述是语义原则，不是关键词匹配或测试句子的白名单。形式选择不新增每条消息必经的分类请求。开发评估允许预先标注多种合理形式，避免把“没有调用指定工具”直接等同语义错误。

### 能力声明必须与执行一致

能力清单记录 ID、版本、支持事件/视图、预算、示例、依赖和证据摘要。状态为 planned、implemented、verified；只有 verified 且当前环境可用的能力进入普通会话提示和接纳范围。开发验证在隔离配置中启用 implemented 能力，避免“尚未验证所以无法测试”的循环。

verified 表示这一版通用能力经过规定验证，不保证每个模型生成的程序正确。每份生成结果仍须校验和试运行。按相关文件摘要使证据失效；不以“排序已通过”建立只支持排序的业务名单。现有 catalog 尚未具备这套逐项状态，属于待实现内容。

## 4. 首先把生成协议做得容易遵守

### 单一契约来源与完整示例

组件与小程序各自提供工具专属的版本、字段和完整可执行示例，由真实 schema、编译能力及测试夹具校验生成。共享的只有形式选择原则；不把两种 planVersion、状态字段和图形协议混写在同一示例中。示例必须实际通过编译与初始投影，覆盖必填元数据和终态，避免模型从残缺片段补猜。

模型仍提交完整 MiniAppPlan。宿主负责程序身份、依赖、预算、状态版本和发布回执。默认字体、主题和通用控件样式由宿主承担；模型主要描述布局、任务状态和计算。预览等到必要样式闭合，不执行模型程序。

### 调整限制，但不改变业务含义

| 项目 | 实施决定与验证边界 |
| --- | --- |
| 顶层常量 | 新能力允许 const 声明有限的数字、字符串、布尔或 null 字面量；数值可带一元正负号。拒绝调用初始化、可变 var/let 和对象共享状态。作用域每次操作重建，状态仍必须显式返回 |
| 常量兼容 | 校验生命周期函数与常量重名、重赋值错误及保存/回放一致性；旧程序保留其运行时版本。不能把模型 var 静默改为 const |
| CSS 与绘图 | 从真实 allowlist 提供精确示例；绘图命令列出所有必填坐标。只扩展能被隔离渲染且可验证的通用语法，不无条件放开任意网页脚本 |
| stateSchema | 继续明确字符串长度、数组规模和对象字段。完整示例展示 enum 也需要长度上界；不根据业务内容猜约束 |
| 原始输入 | 不静默改价格、单位、公式或输入范围。机械规范化必须可追溯，并证明不改变含义；业务修复交给模型或用户澄清 |

### 一次有效纠错

结构、文档、程序可独立检查的错误在同一次诊断中汇总，最多返回 8 条，包含阶段、错误码、路径、实际类型与期望；有依赖的运行检查等待编译通过。返回当前工具名、planVersion 和完整重提说明，不自动合并半份计划。修复结果重新执行所有接纳检查。

沿用同一 PromptRun 共享的 3 次接纳尝试、1 次模型纠错、首次 UI 尝试起 60 秒窗口；换工具不重置预算。错误耗尽后保留旧结果并解释失败。阈值调整须由后续基线论证，不用多重试掩盖协议问题。

### 从初始可运行走向边界可运行

组件试运行除初值外，增加每个输入的最小/最大值、范围内的零、离散选项及步长邻近值；多输入采用受总量上限约束的单变量采样和组合样本。采样策略与上限记录在能力版本中，报告实际覆盖，不能声称穷尽连续空间。

发现异常可返回可纠错诊断；不要自动删掉零输入或把除数改成 1。小程序按声明事件检查生命周期、终态与帧约束。上述检查只能发现部分问题；公式、排序、游戏规则仍使用独立结果核对。

## 5. 复杂交互按完整任务交付

计算采用 init、reduce、advance、project 四个入口。输入、state、随机种子和逻辑时钟显式保存，project 只投影，不推进状态。文档、SVG、Canvas 与受限 Three.js 由可信渲染器负责；模型程序不直接访问 DOM、网络、文件或 Electron。

| 任务族 | 通用能力与完成判据 |
| --- | --- |
| 算法过程 | 序列、步骤与高亮保存在 state；应用按钮、宿主单步、播放共用转换。独立核对步骤、元素守恒与终态 |
| 几何拖动 | 统一坐标变换、指针捕获/取消和键盘或数字替代；拖动后用独立几何公式核对，缩放窗口不能偏移 |
| 动态列表 | 有界重复模板、稳定 key 和事件绑定；增删/重排后仍操作正确项目，展开节点计入预算 |
| 模拟与小游戏 | 固定逻辑步、显式随机源、按键及碰撞状态；验证规则、终态、同种子回放和持续运行后恢复 |
| 三维教学 | 稳定对象 ID、拾取、相机/缩放/选择检查点；交互和说明来自几何状态，并独立核对教学关系 |

播放方式显式区分 none、discrete、continuous。没有推进语义就不展示播放按钮；离散完成态自动停止，连续模拟按固定逻辑步推进。已实现的统一推进不能替代其他任务的验证。

事件携带实例、视口和显示帧身份。连续移动可以合并，按下/松开/取消/点击保持顺序；过期事件不能作用于新对象。隐藏、失焦、停止和卸载均释放按键与拖动。默认暂停，同一聊天视图仅一个实例持续播放。

### 外观与可访问性同时交付

共享设计系统提供主题色、字体、间距、输入、焦点、错误和状态提示。模型负责内容层级与布局，不要求所有任务使用滑块。深浅色、字号、窄屏、键盘和减少动画偏好随任务检查；Canvas/3D 使用语义色与标签，不能用固定浅色替代主题支持。

程序、状态、帧、节点、绘制命令和三维场景分别限额。现有 8ms/步、30fps、32MiB 堆仅是初始配置，不是设备性能承诺。超预算暂停并保留确认检查点；停止释放资源，不丢逻辑步骤伪造流畅。

这一路线能够承接复杂任务，但并非直接运行任意 Three.js 示例。动态列表、三维拾取/相机、持续模拟及教学语义仍需开发；它们保留在第三阶段范围中。

## 6. 保存、修订与动作的完整流程

发布记录保存不可变程序与来源；交互记录保存 inputs、state、rng、tick、程序版本、stateRevision 和投影摘要。恢复不依赖浏览器闭包或 DOM，也不改写原始工具回执。

```text
暂停并冻结新输入 → 排空事件和计算队列 → 一致检查点
→ IndexedDB 草稿 → 分支与 expectedRevision 校验
→ 服务端重投影 / 原子保存 → 幂等回执 → 追问使用确认状态
```

| 场景 | 必须保证的行为 |
| --- | --- |
| 断网、超时、响应丢失 | 保留草稿；同一 requestId 查询回执或重试，确认后才清除对应版本 |
| 保存中继续操作 | 新修改成为下一版；旧回执不清除新草稿 |
| 多窗口或旧分支 | 检查版本和来源；冲突保留双方并提供选择，不静默覆盖 |
| 草稿积累 | 按游标分页可发现全部草稿，不能只显示当前首批 20 项；作用域和排序稳定 |
| fork、复制、导出、回收站 | 继承当前分支可见的确认状态后独立写入；导出静态参数和结果，恢复关联数据 |
| Beta 关闭再开启 | 停止实例并撤销旧请求，保留确认结果和草稿；旧请求不得迟到提交 |
| 按当前结果追问 | 先完成保存；失败可以重试或明确使用已保存值，不能悄悄使用旧状态 |

### 参数变化与程序修订分开

改人数、速度或点位是同一程序的状态变化。增加规则、改变任务或交互才生成候选程序，旧版本仍可用。跨组件与小程序切换也要经过修订确认。

兼容输入按含义、单位及约束迁移，内部 state 默认重新 init。若需要保留进度，运行受限迁移函数后再次验证和投影；展示保留、重置和丢弃的内容。用户确认时重新核对来源版本，以原子方式切换；失败回到旧版本。输入名字相同不足以证明兼容。

### 动作只走登记的宿主入口

程序提供结构化动作意图，宿主检查登记项、参数、当前状态与来源。涉及外部操作时先保存，再经过现有工具权限；执行结果作为独立记录返回。加载、计时器、iframe 消息和模拟事件不能自行取得授权；继续提问须由明确用户操作触发。

完整恢复矩阵覆盖断网、多窗口、取消、重载、分支、删除恢复和 Beta 切换的组合。已有计数器流程或单个刷新成功不能替代矩阵。当前基础保存已有报告，草稿分页、迁移确认和登记动作仍待补齐。

## 7. 实施顺序与验收

每步留下可操作成果、Markdown 记录和 PDF，区分设计目标、已实现和已验证。下面保留原第三阶段范围，按风险调整先后。

| 步骤 | 交付与退出条件 |
| --- | --- |
| 3A 基础契约 | 复用现有隔离计算、编译、可信渲染和旧组件适配；新常量/事件能力变更补相关回归 |
| 3B 首批完整任务 | 先完成完整示例、精确诊断、边界采样和能力登记，再用真实模型验证生成、操作、保存、刷新、追问及基础视觉 |
| 3C 恢复与修订动作 | 草稿分页、恢复矩阵、多窗口冲突、迁移确认和登记动作；失效请求、错误迁移不得覆盖正确状态 |
| 3D 复杂交互与泛化 | 动态列表、几何拖动、持续模拟/游戏、三维拾取/相机/教学；独立正确性、外观、无障碍与资源检查 |
| 3E 综合验收 | 三阶段开发完成后执行完整 CI、封存集和人工语义验收；输出总报告，发布走既定流程 |

### 下一批具体工作

- 先按本批缺陷做通用契约修复：完整示例与工具版本隔离、顶层只读常量、成组诊断和输入边界检查；每个改动绑定失败证据及有意义的回归。
- 固定新版本重跑首批 24 次，不与旧版样本混算；保留每次失败、耗时、原始工具参数和发布回执。
- 对成功生成的程序逐一完成独立结果核对、真实 UI 操作、保存、刷新和解释追问；未生成的样本继续留在完整任务分母中。
- 补齐能力清单与证据失效机制，再推进 3C 和 3D。验证登记按通用能力，不能变成八个测试用例的白名单。

### 泛化评估不缩减

完整集合保持 48 个初始任务：16 小程序、12 组件、12 文字、4 澄清、4 能力缺口。按任务族划分 32 个开发、16 个封存，每例 3 次；首批 8 例计入开发集。看过并用于调试的封存样本转入开发集，同时补入新封存样本。

指标分别为形式选择、首次生成、预算内生成、任务结果、操作、保存/恢复、耗时和资源。超时、漏调用、取消和失败保留在原始明细与分母；不同指标注明适用分母，不能把“有记录”当成“成功”。完整开发集基线后、封存测试前固定数值质量门槛；本次 8 例不足以设定总体成功率结论。

静默丢失、错误覆盖、权限绕过是阻断缺陷。人工语义验收与完整 CI 按用户安排留到三阶段开发后，开发中继续快速检查和必要桌面自测。本地不构建发布包；发布产物交由 GitHub Actions。

可行性判断：计算、持久化和基本桌面链路已有基础；当前主要风险是生成契约、任务语义与复杂交互覆盖。各批以实际证据决定是否进入下一步，不依据演示视频或累计测试数量宣布阶段完成。
